# Kumihimo アーキテクチャ方針

- 状態: 初期ドラフト
- 更新日: 2026-09-03

## 対象環境

- プラットフォーム: iOS（iPhone／iPad）
- 最低対応OS: iOS 17
- 言語: Swift
- UI: SwiftUI
- ナビゲーション: `NavigationStack` を基本とし、利用可能な幅に応じて編集画面内を適応配置する
- ローカル永続化: SwiftData
- 外部依存: 初期段階では使用しない

## 設計方針

MVPでは、理解しやすい単一アプリ構成を採用する。機能ごとにコードを分けるが、早い段階で過剰なレイヤーやモジュールを導入しない。

推奨構成は次のとおり。

```text
Kumihimo/
  App/
  Domain/
  Features/
    BraidSimulation/
    Home/
    ProjectEditor/
    Preview/
  Persistence/
  DesignSystem/
  Resources/
KumihimoTests/
KumihimoUITests/
```

実際のXcodeターゲット名やディレクトリ名は、プロジェクト作成時に確定する。

## 責務の分離

### View

- 画面表示とユーザー操作を担当する。
- 保存処理や複雑な変換ロジックを直接持たない。
- 小さな行表示や空状態は独立したViewへ分ける。

### 画面状態

- 読み込み中、空、一覧、エラーなど、画面に必要な状態を表現する。
- 並べ替えや削除対象の管理を担当する。
- SwiftUIの標準的な状態管理を優先し、不要な独自フレームワークを導入しない。

### Domain

- 組み方、糸、色配置、作品といった、UIに依存しない概念を表す。
- 将来のシミュレーション計算はDomainへ置き、SwiftUIから分離する。

### Persistence

- SwiftDataとDomain／画面表示の境界を担当する。
- Previewやテストでは、メモリ内ストアまたはテスト用実装へ切り替えられる形にする。

## 初期データモデル

保存作品は、概念上次の情報を持つ。

```swift
struct KumihimoProject {
    var id: UUID
    var name: String
    var selectedBraidPresetID: BraidPresetID?
    var standKind: BraidStandKind
    var threadCount: Int
    var threadAssignments: [ThreadAssignment]
    var thumbnailData: Data?
    var createdAt: Date
    var updatedAt: Date
}
```

これは概念モデルであり、そのまま永続化型にすることを強制しない。`BraidPresetID`、`ThreadAssignment`、`ThreadColor` の具体表現は後続の技術検証で確定する。

`selectedBraidPresetID` は任意である。組み方を選ばず、糸本数と色配置だけの作品も有効な保存データとして扱う。

`ThreadAssignment` は少なくとも、天板上で変わらない位置番号と色IDを持つ。配列の添字だけを永続的な位置識別子として扱わない。

`standKind` は組紐台の種類（`BraidStandKind`: 丸台 `round`・角台 `square`。2026-09-24、Task 058）。SwiftData には
既定値 `"round"` つきの文字列の列 `standKindRawValue` として保存し、型のついた `standKind` を通して読む。**台を持たない
既存の保存は、この既定値で丸台として開く**（前のスキーマで書いた store を開く試験 `aSaveWrittenBeforeStandsOpensOnARoundStand`）。
知らない値も丸台として読む。プリセットの台は書かずに**レシピの台（`BraidStand.kind`）から読む**。導出は `kind` を読まない。
組ひもディスクの組み方は `round*` の台に置いてあるので丸台に数える。

### データ上の不変条件

- `id` は作品作成時に生成し、その後変更しない。
- `name` は空白文字だけにしない。
- `threadCount` は正の値とする。
- `threadAssignments` の有効な位置数は `threadCount` と一致する。
- `selectedBraidPresetID` がある場合は、そのプリセットが現在の糸本数と台に対応している。
- `updatedAt` は作品内容の保存時に更新する。
- 色は表示名だけでなく、再現可能な色値を保持する。

## 編集セッションと保存

作品編集画面は、SwiftDataの永続化モデルをViewから直接編集しない。画面を開いた時点の内容から `ProjectDraft` を作り、保存操作が完了したときだけ永続ストアへ反映する。

これにより、次を区別する。

- 新規保存: 新しいIDで作品を作成する。
- 上書き保存: 開いている作品のIDを維持して内容と `updatedAt` を更新する。
- 名前をつけて保存: 新しいIDと作成日時で複製し、元作品を変更しない。

名前をつけて保存した後は、新しく作成した作品を現在の編集対象とする。

## 色カタログ

- UIは任意色を作るカラーピッカーではなく、`ThreadColorCatalog` が提供する有限の色一覧を使う。
- **一覧はハマナカ アメリーエフ《合太》の30色**（色番号 501〜530。2026-09-26 の作者の決定、Task 065。
  その前は西陣の糸屋の38色〔Task 063〕、さらに前は仮の12色）。色番号・呼び名・色値の正本は `docs/colours.md`。
  色は安定したID（色番号から作る、例 `amerry-f-501`）、色番号、呼び名、再現用の色値を持つ。**公式の色名は無く、
  呼び名は審査側が付けた目安**なので、画面の主な表示と読み上げは色番号が先（「501、オフホワイト」、台の糸は
  「糸3、501、オフホワイト」）。色値は見本画像から取った近似で、測った値ではない。既定の色は 501 オフホワイト。
- **それまでのIDは読み替える**（`ThreadColorCatalog.formerIDs`）: 仮の12色からと西陣の38色からの2表。どちらも
  CIEDE2000 でいちばん近い色、ただし**既定の色だった `natural`・`zoge` は新しい既定の 501 へ**。38色は30色より
  多いので多対1になり、12色でも `white` と `natural` が同じ 501 になる。`color(for:)`・`contains` は古いIDでも
  新しい色を返し、作品は次に保存したとき新しいIDで書かれる（`KumihimoProject` が書くときに読み替える）。
  **読み替え表は保存済みの作品への約束なので消さない。**
- 永続データには表示順ではなく安定した色IDを保存する。色IDは糸の並びの JSON の中にあるので、
  一覧を替えても SwiftData の移行は要らない。
- 組み方の見本配色（`BraidMethodCatalog`）は、出所の写真から測った糸の色に CIEDE2000 でいちばん近い30色。
  **1つの配色の中で違う色だった糸が同じ色に集まったら、近いほうが残り、もう一方を次に近い色で分ける。**
  **例外が2つ**（作者の決定、2026-09-26）: 八つ金剛返し組の淡い黄と丸源氏組の生成りは、写真の2色の差に近づけるため、
  いちばん近い 529 ではなく 501（529 は相手の糸の 504 と ΔE 8.0 で見分けにくい）。
  測り方は `Scripts/task063/measure_colourings.py`（Task 063 の値のまま）、選び方は
  `Scripts/task065/choose_colourings.py`、近い色は `Scripts/colours/nearest.py`。
- 色を見分けたいだけの試験は、一覧を順に回さず、自分で書いた12個のIDを使う（`KumihimoTests/TwelveColours.swift`）。
  一覧が変わると、どの糸が同じ色かが変わってしまうため。この12個は仮の12色のIDで、30色では `white` と
  `natural` が同じ色に描かれるが、これを使う試験は糸をIDで見分ける（描いた色では見分けない）。

## 組紐台の俯瞰図

- 最初の表現は、円形の天板、中央の穴、外周から中央へ伸びる糸に限定する。
- 糸の位置は12時方向を基準に時計回りで安定して割り当てる。
- 描画の座標計算とタップ判定をView本体から分離し、糸本数に応じて等間隔に配置する。
- 見た目の糸が細くても、操作用のタップ領域は最低44×44ポイントを確保する。

## シミュレーション境界

シミュレーション機能は、入力と結果の境界を次のように扱う。

```text
入力: 糸本数 + 位置ごとの色ID + 組み方プリセット
出力: 安定した結果ID + 表示名 + 手順検証用の糸経路 + 完成表面パターン + 2Dサムネイル表現
```

プリセット一覧と計算処理はUIから分離する。ユーザーが保存した組み方を将来追加できるよう、UIは組み方の出所を固定しない。ただし初期実装ではアプリ内蔵プリセットだけを対象とする。

最初のプリセットは16本の丸源氏とする。資料から読み取った1周期を、上下の外側2本の交換、左右の外側2本の交換として純粋なDomain計算にする。順序付き移動イベントと糸位置ごとの連続した3D経路は、組み手順を検証するDomain結果として保持し、完成外観の描画には直接使用しない。

丸源氏の完成外観は、実物3例と照合した位置別配色から64枚の正規化表面パッチへの対応を別のDomain結果として生成する。2Dサムネイルと3D詳細はこの表面パターンを共通の正本とし、3Dでは単一の円筒状表面メッシュへ変換する。これにより、手順検証の自由空間内の糸経路と、締められた完成表面を区別する。

3D詳細はiOS 17で利用できるRealityKitの非AR `ARView` をSwiftUIへ埋め込む。カメラ映像やARセッションは使用せず、アプリ内で生成したチューブ状メッシュを表示する。完成プレビューでは端面を生成せず、同じ周期の表面メッシュを長手方向へ反復配置して、表示領域の外まで続く長尺の組紐として見せる。操作は長軸回転、ピンチ拡大縮小、ダブルタップと画面上のボタンによるリセットに限定し、端面が見える長軸の傾斜は行わない。

## 適応レイアウト

- アプリターゲットはiPhoneとiPadをネイティブにサポートする。
- iPhoneのコンパクト幅では、従来の1列スクロールと `NavigationStack` を維持する。
- 十分な横幅がある場合、作品編集画面は配色設定とシミュレーション結果を左右へ分ける。**組み方の詳細（3Dと模様図）は右列を置き換えず、どの幅でもシートで開く**（iOS 18 以降は `.presentationSizing(.page)`。2026-09-24、Task 058）。回転や幅の変化で詳細が閉じたり移ったりしない。
- iPadという端末種別だけで分岐せず、Split View、Stage Manager、画面回転、Dynamic Typeを含む実際の利用可能幅に応じて配置を切り替える。
- 狭いiPadウインドウではiPhone相当の1列構成へ安全に戻す。

初期の3D形状は、実物3例との照合で確認した配色傾向を観察するための技術プレビューである。糸の厳密な上下関係、張力、締め具合、断面形状はまだ物理シミュレーションしないため、UI上で照合済みの範囲と未検証事項を明示する。

実際の組紐結果に見える根拠のない装飾画像を、シミュレーション結果として本番表示しない。検証途中のアルゴリズムを表示するときは、根拠と限界を仕様に記録し、画面上でも試作であることを明示する。

## ナビゲーション

初期画面をアプリのルートとし、次の遷移を想定する。

```text
ホーム
├── 新しく編む → 作品編集（未保存の新規案）
└── 保存作品   → 作品編集（既存作品の詳細）
```

画面遷移時は、可能な限り作品全体ではなく作品IDまたは編集用状態を渡す。戻る操作はiOS標準の挙動を維持する。

## サムネイル

- サムネイルは作品の派生データとして扱う。
- 元の糸配置や組み方を正本とし、サムネイルを唯一のデータ源にしない。
- 生成前または復元不能の場合はプレースホルダーを表示する。
- 起動画面の初期実装では、実レンダリング処理を作らずプレースホルダーでよい。

## エラー処理

- 保存データの読み込み失敗を、作品が0件である状態と混同しない。
- ユーザーが対処できるエラーには、短い説明と再試行手段を用意する。
- 開発者向け詳細をそのまま画面に表示しない。

## テスト方針

優先して自動テストする対象は次のとおり。

- 保存作品の更新日時順の並べ替え
- 作品の追加、更新、削除
- データモデルの不変条件
- シミュレーション計算の既知入力と期待出力
- ナビゲーションに渡す作品ID

UIテストでは、主要なユーザーフローを少数に絞る。

1. 空状態から新規作成を開始できる。
2. 保存作品を開ける。
3. 作品を確認付きで削除できる。

### 試験が読むメッシュは、1回の実行で1度だけ作る（2026-09-23、Task 056）

**同じメッシュを読む試験は `KumihimoTests/SharedMeshes.swift` から受け取る。**配色と大きさを鍵にして、
最初に頼まれたときに作り、あとの試験には同じものを渡す。Debug ビルドでは丸源氏のメッシュ1つに
約 2.6 秒、平源氏に約 3.6 秒かかり、**Task 056 の前は約 40 件の試験が同じ数個をそれぞれ作り直していた。**

- **渡しても試験の中身は変わらない。**メッシュは値で、生成器は呼び出しの間に状態を持たない。
  渡されるのは、その試験が自分で作ったはずのメッシュそのものである。
- **作ること自体を問う試験は共有しない。**2回作って同じかを見る試験（`meshGenerationIsDeterministic`）、
  悪い引数で `nil` が返るかを見る試験は、これまでどおり `generate` を直接呼ぶ。
- **製品コードの側は共有しない。**`BraidFamilyDrawing.mesh(for:on:)` のように製品の経路を通すことが
  試験の中身であるものも、直接呼ぶ。
- **共有する理由は、同じメッシュを何度も読むことにある。**作ったメッシュは実行の終わりまでメモリに
  残るので、1回しか読まないメッシュのためだけに使う理由は無い（共有するものと同じ繰り返しに
  並んでいるなら構わない）。

## 遮蔽マップをマテリアルのどのスロットへ与えるか（2026-09-05）

組紐の表面の谷の陰は、糸ごとに生成した遮蔽マップで描く。このマップを与える先には2つある。

- `baseColor` へ色として掛ける — **直接光**を弱める。
- `ambientOcclusion` スロットへ与える — **環境光**を弱める。

**両方へ与えるのが遮蔽マップ本来の使い方であり、明暗の付き方が大きく変わる。** Task 007E
段階4a の実測では、平源氏の長手方向の輝度変調が `baseColor` のみで 0.463、両方で 0.618
だった（資料の完成写真は 0.670〜0.884）。定数は一切変えていない。

**非対称は Task 005J 段階1（2026-09-06）で閉じた。両方とも両スロットへ与える。**

- 平源氏（Task 007E 段階4a 以降）: 0.463 → 0.618。
- 丸源氏（Task 005J 段階1 以降）: 0.489 → 0.617。資料の丸源氏は 0.738〜0.814。

### 訂正: 丸源氏の「0.605」は単色の値ではなかった（2026-09-06）

ここには当初「丸源氏は同じ手順で測ると 0.605」と書いてあった。**この数字は手順を満たして
いない。** 測定手順書は「単色の行」を要求しているのに、0.605 は青と桃の2色の fixture 1 で
取られていた。行の中で色が替わるぶんだけ値が上がる。単色フィクスチャで測り直すと **0.489**
である。

**間違えた理由**: 平源氏では主値の fixture B がたまたま面全体で単色だったため、「そのとき
手元にあったフィクスチャで測る」ことと「単色の行で測る」ことが一致していた。丸源氏へ数字を
1つ並べたとき、この一致が偶然だったことに誰も気づかなかった。**手順が要求する条件は、
フィクスチャを替えるたびに満たされているか確かめること。**

なお Task 007E の判断はこれで動かない。平源氏の合格条件は「下限 0.5 と目視」であり、
0.605 は参考として並べただけで判定には使っていない。

### この指標が掛けられない帯

変調 `(p95 − p5) / p95` は p95 で割るので、**p95 が小さい帯では発散する。** 黒や紺のように
極端に暗い帯は、分母が小さいぶんだけ値が跳ね、明るい帯と並べて比べられない。単色で続くのが
そういう帯しかない資料は、この手順では測れない。除外して理由を書くこと。

Task 005J 段階1 で bookA p94（丸源氏の完成写真）を外したのがこれである。長手方向に1色で
続くのは黒の縁取りだけで、山形の側は白・橙・桃が交互に来るため単色の帯が取れない。

手順の正本は `docs/measurement-procedures.md`。生データは
`.build/task007e-screenshots/` と `.build/task005j-screenshots/` にあるが、**`.build/` は
git の管理外なので、判断に効く事実は正本の側へ写すこと。**

## 畝の高さと模様の縦横比は、実物写真からは分離できない（2026-09-06）

Task 005J 段階2b で分かった。**写真から測れるのは「見かけの山形密度」という両者の組み合わせ
1つだけであり、片方を動かせばもう片方も動かさないと写真に合わなくなる。**

見かけの密度 = 見かけの紐幅 ÷ 山形のピッチ。山形のピッチは `patternAspectRatio` だけで
決まる。見かけの紐幅は `crestHeightRatio` で変わる — 畝を上げれば紐は太る。**幾何に触れて
いなくても、畝を動かせば写真と比べる量が動く。**

### 紐幅の取り方（この数字を書くときは必ず添えること）

見かけの密度は**何を紐幅とするかで変わる。基準を書かない数字は使えない。** 丸源氏では
候補が3つあり、値がこれだけ違う（`patternAspectRatio` 0.65、頂 0.12）:

  公称（平均面）              2 × 半径                              1.96
  **畝の稜線での外径**        2 × 半径 × (1 − 谷の深さ + 頂)        **2.14**  ← これを使う
  メッシュの最大半径          交差で糸が乗り上げるぶんを含む        2.17

**採るのは畝の稜線での外径である。写真が測っているのは紐の外形の幅だからである。**
レンダーの輪郭を実測すると稜線の予測に対して −1.2〜−1.6% で一定して追随し（差は亜画素の
辺の取り方）、メッシュの最大半径に対しては −3.3〜−5.4% とずれ、しかも**ずれが頂とともに
広がる。** 交差で糸が乗り上げる分は局所の瘤であって、輪郭を決めていない。

### 丸源氏の値（紐幅 = 畝の稜線での外径、実物写真は 1.8〜2.15）

  頂 0.12（現状）  見かけの密度 2.14  帯の上端ぎりぎり
  頂 0.24          見かけの密度 2.37  帯の外
  頂 0.353         見かけの密度 2.59  帯の外

**0.12 が帯の内側にあることを据え置きの根拠にしないこと。** 2.14 は上端 2.15 との差が 0.5%
しかなく、紐幅の取り方を1つずらせば（メッシュ最大なら 2.17）外側へ出る。**内か外かは
決められない。**

**据え置きの根拠は「0.24 と 0.35 は明確に帯の外で、0.12 だけが桁違いに帯へ近い」ことである。**
上端からの距離は 0.12 が 0.5%、0.24 が 10%、0.353 が 20% である。

0.353 は「平源氏で決めた 0.45 糸幅ぶんを丸源氏の半径比へ直した値」（0.45 × π / 4）である。
**物理はこれを指すが、写真は反対を指す。** 0.353 を入れて写真へ戻すには
`patternAspectRatio` を 0.75 付近へ動かす必要があり、それは Task 005I を開き直すことになる。

### 番人

`theChevronDensityFollowsTheDeclaredAspectAtAnySize` は当初これを検出しなかった。公称半径

**経緯**: これは一度メッシュの最大半径で書かれていた。交差で糸が乗り上げる分を含むぶん

稜線での外径へ揃え、帯は Task 005I 本来の 1.5〜2.2 に戻した（2026-09-06 解消）。

### 両方の組で「外径」は稜線での外径である

  丸源氏  `MaruGenjiSurfaceMeshData.crestRadius` = 半径 × (1 − 谷の深さ + 頂)
  平源氏  外側の比 `(w/t + 頂)/(1 + 頂)` = 2.611。半厚を1として 外側の半幅 3.786 / 半厚 1.45

メッシュの最大＝稜線での外形であり、丸源氏のような乗り上げ分の差が生じない。丸源氏だけが

### 測るときの落とし穴: 遠近法

レンダーのスクリーンショットから見かけの密度を読むと、**14% ほど低く出る。** 山形は手前の
面にあってカメラに近く拡大されるのに対し、紐幅は最も広いところ＝軸と同じ奥行きで測るため
である。倍率は `カメラ距離 / (カメラ距離 − 外半径)`（4.4 / (4.4 − 0.52) = 1.135）。

Task 005J 段階2b は当初この補正を欠いており、1.87 / 2.06 / 2.21 と報告した。補正すると
2.12 / 2.37 / 2.58 で、**幾何から直接出した 2.14 / 2.37 / 2.59（紐幅 = 畝の稜線での外径）と
0.6% で一致する。** 2つの独立な経路が同じ値を返したので、この組を正本とする。
**スクリーンショットから幾何量を読むときは、必ず幾何と突き合わせること。**

### 測り方（両方に使える）

紐のシルエットの上辺を、輝度が背景と紐の中間値を下向きに横切る点として亜画素で求め、
1手のピッチ2つぶんの移動平均を引いた残差の σ を、ピッチに対する比で表す。

**残差の自己相関でさざ波の周期を求め、1手のピッチと一致することを必ず確認する。**
一致しなければ測っているのは糸のけばであって形ではない。この確認が無いと、bookB p23 の
白い縁糸（周期 r=0.16、糸の直径の1.3倍という物理的にありえない値になる）を資料として
採ってしまう。

平源氏のレンダーでの較正は σ(%) = 9.55 × 頂（頂 0.12 / 0.24 / 0.48 で線形を確認）。

**較正は組ごとに取り直すこと。丸源氏は直線ですらない**（Task 005J 段階2、頂 0.00〜0.48 の
8点）。

  丸源氏  σ(%) = 17.31 × 頂^0.752（残差 0.044、頂 0 で σ 0.02%）

丸い紐のシルエットは接線の包絡なので、畝が高くなるほど隣の畝の谷が隠れて飽和する。平らな
面にはこの飽和が無い。**平源氏の式を引き写していたら大きく外していた。**

丸源氏の端の波形の周期は 1手の山形の 4/9（レンダーで 141px に対し 62px、頂によらず一定）。
平源氏では 1手そのものだった。**組が変われば周期も変わる。**

### シルエット法は丸い紐には使えない（Task 005J 段階2、2026-09-06）

「丸源氏の良い写真が無かった」ではない。**この測り方が丸い紐に向かない。** Task 005J で
実際に試して、根拠が3つ揃った。

1. **実物の外周が滑らかで、畝の列に見えない。** 手元の4枚とも、拡大しても縁は1本の滑らかな
   紐である。**丸源氏には糸が折り返す縁が無く、糸は斜めにシルエットを横切るだけなので、
   滑らかなのが正しい可能性が高い。**
2. **シルエットの特徴が目と1対1に対応しない。** レンダーの端の波形の周期は1手ではなく
   1手の 4/9（141px に対し 62px）。平源氏では1手そのものだった。
3. **較正が飽和する。** 丸い紐のシルエットは接線の包絡なので、畝が高くなるほど隣の畝の谷が
   隠れる。頂を2倍にしても σ は2倍にならない。

**平源氏のシルエット法は、縁で糸が折り返す平たい紐だから成立した道具である。**
Task 008 以降の丸い組み方（八つ金剛・江戸八つ・八つ瀬・唐八つ・江戸源氏・方丈）で畝を
決めるときは、この手順を最初から選択肢に入れず、別の観測量を先に探すこと。

そして測ってしまった場合の危うさも記録しておく。**周期を確認しなければ、資料は現在の
0.12 を追認する。** 各資料の σ を較正へ通すと頂 0.045〜0.193 が返り、0.12 はそのまん中に
落ちる。測っているのは糸のけばと紙・木目のざらつきである。**周期の確認は形式ではなく、
これが唯一の歯止めである。**

## 断面は巡回列である。畳み方は導出であって入力ではない（2026-09-06、Task 020 段階1）

組紐の断面を「表・裏・縁」で型に持つと、平たい紐しか表せない。**断面は糸1本ずつの巡回列
（リング）とする。** 丸い紐はこれだけで表せ、平たい紐は同じリングが2か所で折り返したものと
して表せる。

**宣言するのは巡回順だけである。** 折り返す場所（縁）・表裏・幅の並びは導出する。

  1. 周期を通して2つの升だけを行き来する糸は、長手方向に走る糸（縦糸）である。
  2. その2つの升の対は、リングの反射になっている。**平源氏では実際になっており、
     4組から決まる反射は残り4組も正しく対にする。** これが厚み方向の鏡であり、
     `HiraGenjiWeaveDerivation` が `9-p` と式で書いていたものと同じである。
  3. その反射の軸がリングを横切る2か所が、紐が折り返す場所＝縁である。
  4. **縦糸が1本も無ければ反射は決まらず、折り返しも決まらない。紐は筒のままである。**

丸源氏は全16本が動くので縦糸が無く、筒として出る。平源氏は縦糸8本から反射が決まり、
幅 −1〜6・6列・縁4升が出て、**bookA p96 から読んだ旧来の対応表と16位置すべてで一致する。**

**6列は幾何（弧長）であって、6列とも縦糸が占めるという意味ではない。** Task 021b-1 の占有
履歴では、**片面6列のうち内側4列が縦糸の位置、外側2列（幅0・幅5）は横糸の位置**である。
**数値は動かない**（断面の 6:2:6:2 も 007G の位相も）。付いたのは意味だけである。

**既定の断面は台の周の巡回順（筒）である。** 編み出した組み方は、巡回順を宣言しなければ
筒として出る。推定であることを `BraidCrossSection.Source` が持ち、隠さず表示する。

## 積み重ねの模型（確定版・密に積む）: 上下が両方の組で出た（2026-09-07）

### 模型（これが定義。読みを変えたら別の模型である）

- **段 R** は1サイクルで +1。詰め直し（1ノッチの水平移動）は進めない。
- **Z** は**本の1手（2本同時）ごと**に +1。詰め直しは進めない。サイクルごとに数え直す。
  bookC のエントリ2つが本の1手そのものに対応することは確認済み
  （Z1=糸3と6、Z2=14と11、Z3=8と9、Z4=1と16、Z5=7と10、Z6=2と15）。
- **1手の糸が占める場所**は、行き先と途中で越える場所。**出発点は含めない。**
  「越える場所」は導出した断面の上で測る（畳みがあれば幅の軸、筒ならリングの弧）。
- **各場所の層**: 来た順（Z の順）に**厚さ d の層を密に積む。** その糸の長手座標は
  **その場所での層番号 × d**（0, d, 2d, …）。**R × Z/Z総数 は使わない。**
- **R の物理長 = 各場所の層数の最大 k × d。**
- **覆いの定義（実行前に決めたもの）**: 密に積むと同じ場所の層は d ごとに並ぶので、**接するのは
  層番号が隣り合う2つだけ**（中心距離がちょうど d）。それより離れれば隙間が空く。
  **「同じ場所で上に積まれた糸が下の糸を覆う」＝層番号が隣り合う2つ**、あとが上。
  **閾値は手で置いていない。糸の太さそのものである。**

### サイクルをまたぐ接触は幾何で決まった

**その場所の層数が k に達しているときだけ、前のサイクルの山と次のサイクルの底が接する。**
達していなければ (k − 層数) × d の隙間が空く。

  平源氏  16の場所のうち **8** が k に達する（縁と最外列は 1〜2 層で隙間が空く）
  丸源氏  **16すべて**が k に達する（どの場所も3層）

**この違いは規則ではなく幾何から出た。丸源氏は筒なのでどの場所も同じだけ積み、平源氏は
縁と最外列が薄い。**

## 組み台の力学（作者の前提）: 面に見えるのは、そこに留まっている糸である（2026-09-07、Task 021b-1）

**これは作者が置いた前提であり、この repo での正本である。** Task 021a（到着点どうしを斜めの
直線で結ぶ初期配置）が面で不合格になった原因はここにあった。

### 前提

- 各糸の端には玉（錘）が付いていて、丸台の鏡の縁に沿って、**自分の位置へ向けて外向きに引かれ
  続けている**。円状に外向きの張力。
- 組み上がっていく紐の端にも錘が付いていて、**下へ引かれ続けている**。
- したがって、**どの糸にも常に張力がかかっている**。ゆるんでぶら下がっている糸も、中央で遊んで
  いる糸も無い。**どの区間も張った直線。**
- **自由度は少ない。**

### 前提から出ること

1. **位置に留まっている糸は、外向きの張力で紐の表面のその角度に張り付いている。** 到着の長手
   座標から出発の長手座標まで、**表面に沿った縦の走り**。内側には入らない。「留まっている」は
   張ったままの意味であって、ゆるんでいるという意味ではない。
2. **運ばれる糸は、置かれた瞬間から新しい位置へ外向きに引かれている**ので、古い位置の表面から
   新しい位置の表面まで、**その時点の束の上面に押し付けられた張った直線**になる。渡った直後は
   最新層、次の手が積まれるごとに下の錘で押し込まれ、出来上がりでは**層座標 z の高さの直線**
   として残る（積み重ねの模型そのもの）。**渡りが表面に触れるのは両端だけで、中央で浮いている
   区間は無い。**
3. よって**表面のある角度に見えるのは、そこに留まっている糸だけ**。
   **面の模様 = 位置の占有履歴。**

### 潜らせる手は無い（作者の前提、2026-09-10）

**組紐に「他の糸の下をくぐらせる」という手は、基本、無い。**（作者。「あるかもしれないが
聞いたことがない」）**組み手がするのは、糸を束の上に置くことだけである。**

**したがって上下は手の種類ではなく、順序と張力の帰結である**——後に置いた糸が上、先に置いた
糸はその下、というのは上の力学からそのまま出る。**これは新しい規則ではなく、「潜る」という
手を規則に足す余地が無いことの確認である。**

**効くところが3つある。**

1. **手順表に「くぐらせる」欄は要らない。** レシピが言うのは「どの糸がどこへ、どの順で」だけ
   である（`docs/tasks/025-5-adding-a-recipe.md`）。**bookC の1手＝1本の順序が上下を決めている**
   （「正本の読み方」）ので、資料に上下の指定が無いことは欠落ではない。
2. **自分で編み出す版（Task 020 段階4）でも、入力に潜らせる手を作らない。**
   `BraidDerivation.passingsWithinOneInstant` は「同じ瞬間に2本を動かすと宣言したとき、
   その2本が互いを追い越さずに済むか」を見る番人であって、潜らせる手のための穴ではない。
3. **「くぐる」と書いてある所は、出来上がりの見えの記述である。** Task 007I の「縁の糸が面の腹
   の下をくぐって見える」、`BraidFigure` の `passage` / `isOnTheFace`、丸源氏の
   `BraidCrossingLayer`——**どれも積み終わった紐がそう見えるという話で、手ではない。**

### 詰め直しの入り方（作者の判定、2026-09-10）

**運ばれてきた糸は、相手が出て行った定位置に入るのではない。群の外側に入り、居た糸が1コマ
ずれる。** そして**1周期の最後に詰め直しの手を置いて、定位置へ復帰させる。**

**これは1つの紐の話ではなく、台の使い方の判定である。** bookA 系の絵（矢印と手の吹き出しだけ
で、着地のノッチを描かない）から手順表を起こすとき、**着地スロットはこれで決まる。**
bookC の表がその形をそのまま刷っている——**組みの手のあとに詰め直しの手が続く**。

**効くのは正味の置換である。** 八つ金剛S でいえば、「対角の入れ替え」（紐が回らない）ではなく
**「全糸が3コマ反時計回り」**（紐が回る）になる。**回るほうが bookA p54 の point! 欄
「鏡の下でひもが回転しながら組み上がります」とも、Task 008 の参照出力（市松・斜線の出し分け）
とも合う**（`docs/tasks/008-yatsu-kongo-8.md`）。

## 組み上がりの解き方は準静的である（作者の決定）（2026-09-07、Task 022）

**これは作者の決定であり、この repo での正本である。**

> 揺れを見たいのではない。**動力学は要らない。** 糸は物体に沿って曲がったら、あとは剛体の
> ように動かなくてよい。

したがって Task 022 の模型には、**質量・重力・慣性・減衰・時間刻みが1つも無い。** 一手は
次の4つで、それだけである（`docs/tasks/022-braid-on-the-stand.md`）。

  運ぶ    指定の糸の自由部分を、他の全部の糸の上を通して新しい角度へ移す
  張る    両端を留めたまま糸をまっすぐにし、余りを縁側へ送る
  固定    束に取り込まれた区間を剛体として固定し、以後動かさない
  記録    各手の後の全カプセル中心を書き出す

**張った糸とは、両端のあいだで、他のすべての外を通る最短の道である。** 拘束は2つだけ——
太さ d のカプセルどうしが通り抜けないこと、隣り合う球の距離が d であること。**当たった糸の
上で曲がり、当たっていない区間は真っ直ぐになる。**

### 組み点の深さは錘の比で決まる

玉が糸を縁の外へ引き、吊りおもりが束を下へ引く。糸は束を出て上と外へ走り、穴の内側の丸めに
当たるので、真っ直ぐな区間はその丸めへの接線である。釣り合いは

    糸の本数 × 玉の重さ × sin(水平からの角度) ＝ 吊りおもりの重さ

**16本・玉 100 g・吊り 570 g で、組み点は鏡の上面から −1.658 d**（`Scripts/task022/stand.py`
の `braiding_point_depth`）。**束の半径に依るので、半径 2.546 d（円周の読み）で計算すると
−1.665 d になる。正しいのは正16角形の読みのほうで、−1.658 d である**（2026-09-07 に訂正）。

**これは「結び目が穴の口へ上がる」という 022-1 の動力学の観察と同じことを、2つの錘から一度
だけ解いたものである。以後は定数として記録する。**

### 束の周りに糸が立つ半径

**糸は束の周りに互いに接して立つ**ので、中心間距離は d、中心は1辺 d の正16角形の頂点であり、
半径は **d ÷ (2 sin(π/16)) = 2.5629 d** である。**周長を 16 d とする読み（半径 2.546 d）は、
隣どうしを 0.9938 d に置いてしまう**（何も起きないうちから 0.6% 食い込んでいる）。断面の
「周長＝糸16本」はこの正16角形の周長のことである。

**product code は半径を持っていない。** `BraidCrossSection` は**並び順だけ**で、寸法を1つも
持たない。「周長 16 d」の読みが数値に効いているのは**平源氏の断面比 3.3359 の導出**
（周長＝糸16本・厚み＝糸2本）と `HiraGenjiSurfaceMeshGenerator` の寸法であり、そこでは
**円周と正16角形の周長の差 0.7%** がそのまま乗る。**Task 022 は多角形の読みを使う。
既存の値は動かさない**（凍結中の生成器は Task 022-4 まで触らない）。

## 山は糸の半径から出る（作者の決定）（2026-09-08、Task 024）

**これは作者の決定であり、この repo での正本である。**

**糸の各位置（留まりの場所、交差点）の基準の高さに対して、別の糸がくぐる可能性のあるところ
では、越える糸を +d/2、くぐる糸を −d/2 だけ表面の法線方向にずらした山を作る。**
**山の形は弧でも直線（三角）でもよい。交差点での中心間距離はちょうど d になり、貫入は構成で
消える。solver は使わない。**

**裏付け**: **平源氏の膨らみの測定 0.45（輪郭、Task 007E）と 0.40〜0.50（物理の重なり）は
d/2 = 0.5 に一致する。** **これまで観測値として与えていた膨らみが、糸の直径から出る。**

**山の幅も d である**——中心から ±d/2 で最大、その外で 0 に戻す。**定数は d だけ。**

### 山の向きは面の法線で決める（追記、2026-09-08）

**山の向きは対の関係（どちらが上か）から決めない。糸が今いる面の外向き法線で決める。**
**白（基準面）を 0 とし、表の糸は +d、裏の糸は −d に既にずれている。山はそのずれている側へ
だけ膨らむ。実世界で重ね合わせの上下が逆になることは無い。**

**面は `BraidCrossSection` の畳みが各場所に与えている**（表／裏／縁。丸源氏は全部が外周で
法線は半径方向）。**糸が表の場所に動けば表、裏の場所に動けば裏。腹や芯を横切る渡りは 0
（膨らまない）。**

**平源氏の素の厚みは 2 d である**（追記、2026-09-08）——**表の縦糸は +d/2、裏は −d/2。
触れ合っている。3 d ではない。**

**横紐（腹を横切る渡り）は 0 の高さを、自分の Z（積み重ね模型の層）で通る。厚み方向に常設の
層は持たない。** **横紐が通るところだけ、表の縦糸は +d/2、裏は −d/2 押されて（山）、そこで
厚みが 3 d になる。それ以外は 2 d。**

**横紐どうしは厚み方向に重ならない。長手（Z）に並ぶ。** 積み重ね模型の**1列1サイクル ＝
縦糸の着地1層 ＋ 横糸の通過2層**のとおり、**横紐2本は Z で d 離れている**——
「表裏の交差｜横紐 A｜横紐 B｜裏表の交差」で**横紐が Z に 2 d を占める。**

**一つの区間に複数の山が付くときは、足さずに重ねる（各点で最大を採る）。打ち消しは起きない。**

**同じ場所を前後で引き継ぐ2本は、積み重ね模型のとおり、後から来た糸の到着層が前の糸の出発層の
一つ上である。端どうしは d 離れる。これは重なりではなく層の段差である。**

## 二つの錘の下で組む（作者の決定）（2026-09-12、Task 036）

**これは作者の決定であり、この repo での正本である。** 指示書は

> 連続体なので、潰れたときには影響を受けた点は座標も移動するし、紐に余りも出るはず。

> オモリが適切なのだろう。**適切なオモリがあるということは、始点と終点を最短で結ぶという

> 一手を進め、上に乗ったのなら、下にあったものはオモリがあるとはいえ、最短を通ろうとした
> 紐の力に負け、位置は避ける方向へズレるはず。

- **力は端の二つだけ。** 各糸の縁の端に玉 T（糸に沿って一様な張力、全糸で同じ）、束に取り込まれた

  s は束の下がり）。**T の絶対値は消え、残る数は W ÷ 16T だけである。**
- **「適切なオモリ ＝ 最短で結ぶ」は物理として厳密である。** 一定の張力の糸の釣り合いは、両端のあいだで
  他のすべての外を通る最短の道であり、張力の大きさは形に残らない。**022 の「張った糸とは最短の道」は

- **上下は規則ではない。** 運ぶときに他の全部の上へ置き（後手は Z が上）、非貫入が通り抜けを禁じる。
  **必ず上を通る。** 反転 0 は番人であって規則ではない。
- **糸ごとのテンションの設定は入れない。** 一度求め、同日に撤回した。「横紐を強く引けば横方向に扁平」は

  外れるものが出ても、それは記録して見る対象である。
- **ピッチは出る側に回る。ただし予言つきで。** 1 サイクルあたり (16T − W)·p ＋ T·(渡りの長さの和) の形に

## 端を握るとは、最後の交差を握ること（作者の決定）（2026-09-14）

**これは作者の決定であり、この repo での正本である。**

> 端を握っているから、重力もないし摩擦がなくても勝手に解けないんじゃないかな。
> ——糸の両端ではなく「その糸の最後の交差」と読んで良い。

### これが決めること

- **一手の糸の固定端は、その糸が直前に置かれ、後の手に乗られた交差である。** そこから縁までが自由部で、
  張った最短の道（他のすべての外を通る）で置く。**力も錘も要らない。幾何だけ、一手ずつ。**
- **位相と位置は別である。** 端を握った組紐は摩擦が無くても解けない（位相）。しかし摩擦の無い糸では交差は
  糸に沿って滑る（位置）。022 は糸の両端——結び目と半径 62.5 d の縁——を握ったので、交差が結び目へ滑って
  束が円錐に開いた。**それは solver の失敗ではなく、その握り方での正しい答えである。**
- **実物で交差が滑らないのは、置かれた交差が次の層に埋められて動けなくなるから。** それが摩擦の仕事であり、
  重力とは関係が無い。**「乗られた区間は固定する」がその模型である。** 積み重ね模型で長手を与えた 037 は、

## 一手の検証と解法の上限（審査側の判定、同僚の審査を経て）（2026-09-16、Task 041）

### 筒の族は「運びが一方向か、両方向か」でも分ける（Task 059、2026-09-24）

**`BraidFamily.roundTube(threads:turning:)`。`turning` は紐から読む**（`BraidTurning.of`）: 周期ごとに組みの手
（詰めの `closing` は除く）の運びを短い向きで数え、**同じ周期に逆向きの運びがあれば `.bothWays`、なければ `.oneWay`**。
半周（8場所の盤の4場所、4場所の盤の2場所）と動かない糸は向きを持たないので数えない。名前は読まない。

| 紐 | 読み | 理由 |
| --- | --- | --- |
| 八つ金剛 S・Z | 一方向 | 全糸が同じ向きに2場所 |
| 八つ金剛返し | 一方向 | 表の替わり目で向きが変わるが、どの周期も1つの向き（持ち替えの4場所は半周） |
| 丸四つ | 一方向 | 運びが全部半周で、向きが無い |
| 江戸八つ | 両方向 | 各対の片側4本が +2、もう片側が −2 |
| 丸源氏 | 両方向 | 組みの手が ±13 ノッチ |

**8本の筒は2つの族を1つの描き手で描き、形の値を族ごとに持つ**（`RoundTube8SurfaceMesh.shape` と
`.shapeTurningBothWays`）。行（台の場所1つに1行、8行）・メッシュとカードの作り・「見えるのは最も高い目」という規則は同じで、
族が選ぶのは**場所に何が見えるか**（一方向: そこに立っている糸の升。両方向: その場所の上を渡った糸の目）、**糸が何として見えるか**
（`RoundTube8SurfacePattern.bundle`: `.standard` と `.bothWays`）、**1周期の長さ**（`pitchOverDiameter(for:)`: 0.807 と 0.50）、**山の高さ**
（`runHeightOverRadius(for:)`: 0.44 と、それ以下の両方向の族の値）、**糸筋と陰の地図**（`RoundTube8StrandTexture.maps(on:)`。縞の角度・本数・
起伏も族ごと: `fibreStripeAngleDegrees(for:)` など）。**描き手を分けなかった理由**: 分かれるのは形の値と目の決め方だけで、
作りを複製すると一方の直しが他方へ届かなくなる。族を分けた理由は「形の値は族のもの」（`BraidFamilyShape`）を
守るためで、族を分けずに描き手の中で選べば、同じ族が2組の形の値を持つことになる。

**両方向の族の目は「上を渡った糸」が立てる**（Task 059 追補6、審査側、2026-09-25）: 手順表の1手で動く糸は、元の場所から着地の場所まで
短い向きに回るあいだに、その間の場所に居る相手の組の糸の**上を渡る**。**渡られた場所に目が1つ立ち、行はその場所、色は渡った糸**
（`RoundTube8SurfacePatternGenerator.passes`）。誰がどこに居るかは、その瞬間の始めの糸ごとの場所で読む（1手1瞬間の表では、着地の場所に
前の糸がまだ居ることがある——江戸八つ組の 4→11→12 は1つの運びとして最初の図に書かれる）。高さは、周期の前半の手の目が後半の手の目より
半周期前（目の真ん中＝その段の糸の着地の時刻）。**1周期に、どの場所にも目が1つ、どの糸も目1つ**でなければ描かない（`nil`）。
表から読むだけで、組み方の名前は読まない。江戸八つ組では、左側の組（場所 1・3・5・7）の糸が偶数の場所の行に、右側の組の糸が奇数の場所の
行に出て、**行は組ごとに1行ずつ交互**、1本の行の中では2色が1周期ごとに入れ替わる（色は2周期で戻る）。教科書 p.65 左の配色（左側4本と

## 手順のアニメーションの台本（Task 061、2026-09-25）

**手の台本（`BraidStepScript`）は `BraidMethod` の `steps` を数え、向きは表のノッチの短い向き、寄せる手は数えない。**
手は各表の `steps` の1つ（1手1本、`.oneStepAnInstant` の表は刷られた1手＝2本）で、表が複数あれば表の順。`closing`（隣へ寄せ直すだけの手）は
手に数えず、周期の最後の手の終わりに動かす（作者「仮置きは次のための調整なので…段を増やす必要はない」）。ディスクの仮置きとずれは
`BraidDiskNotation.method` の中で済んでいるので、台本の糸は場所の上か、その脇（`BraidStandState` の列の2番目、来た側）にしか居ない。
**向きは場所からではなく表から読む**: `steps` の運びと同じ順の `braidingMoves` の短い向き（ノッチの前向き＝右回り）。場所だけでは半周の運び
（丸四つ組、返し組の持ち替え）の向きが決まらないからである。上を渡る糸は、その向きに通り過ぎる場所に居る糸（Task 059 と同じ読み）。
1回りは、表の列を丸ごと回した回数で、どの場所の色もはじめに戻るまで。組み方の名前は読まない。

**そのために、`BookDiskKongo.rounds` は運ぶ糸の着地を来た側に書く**（Task 061）。それまでは着地をいつも行き先の休みのノッチの1つ手前
（左回り側）に書いていたので、半周の運びでは、その1ノッチが短い向きを決めてしまい、返し組の S の表の持ち替え（本の p.38 [4]、左回り）が
右回りに読めた。来た向きは、その糸が本のディスクで動いた手の短い向きの和。**場所の出入り（`BraidMethod`）は変わらない**ので、導出・形状
ハッシュ・カードの画素は前と同じである。

**まとめた手の持ち替え部分は、表の付けたりから分けて見せる。導出は読まない**（Task 062）。返し組の持ち替え（本の p.38 [4]・[8]、
作者「隣の紐を向こう側へ跨がせる」）は、表の中では直前の段の運びに足されて糸1本の1手になっている（1つの表で1本の糸は1回しか運べない）。
`BookDiskKongo.rounds` はそのとき、段の運びが糸を置いた場所と、2つの部分それぞれの本のディスクでの向きを `BraidDiskNotation.handOvers` に
書き残す。台本は、その運びを置いた場所で止め、分けた運びのうち最後のもののあとに、持ち替えを1本ずつ手として置く（持ち替えは相方1本の上を
渡る。閉じの寄せ直しとは違う）。表の短い名前（「Sの組み」「Zの組み」）と持ち替えの名前（「持ち替え」）も表の付けたりに持たせ、画面は
表が複数ある組み方でだけ出す。`BraidMethod` と導出は `handOvers` も名前も読まない（付けたりを外した表で同じ `BraidMethod` になる試験がある）。
