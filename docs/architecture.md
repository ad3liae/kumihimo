# Kumihimo アーキテクチャ方針

- 状態: 初期ドラフト
- 更新日: 2026-09-03

## 対象環境

- プラットフォーム: iOS（iPhone／iPad）
- 最低対応OS: iOS 17
- 言語: Swift
- UI: SwiftUI
- ナビゲーション: `NavigationStack` を基本とし、利用可能な幅に応じて編集画面内を適応配置する
- ローカル永続化: SwiftData
- 外部依存: 初期段階では使用しない

## 設計方針

MVPでは、理解しやすい単一アプリ構成を採用する。機能ごとにコードを分けるが、早い段階で過剰なレイヤーやモジュールを導入しない。

推奨構成は次のとおり。

```text
Kumihimo/
  App/
  Domain/
  Features/
    BraidSimulation/
    Home/
    ProjectEditor/
    Preview/
  Persistence/
  DesignSystem/
  Resources/
KumihimoTests/
KumihimoUITests/
```

実際のXcodeターゲット名やディレクトリ名は、プロジェクト作成時に確定する。

## 責務の分離

### View

- 画面表示とユーザー操作を担当する。
- 保存処理や複雑な変換ロジックを直接持たない。
- 小さな行表示や空状態は独立したViewへ分ける。

### 画面状態

- 読み込み中、空、一覧、エラーなど、画面に必要な状態を表現する。
- 並べ替えや削除対象の管理を担当する。
- SwiftUIの標準的な状態管理を優先し、不要な独自フレームワークを導入しない。

### Domain

- 組み方、糸、色配置、作品といった、UIに依存しない概念を表す。
- 将来のシミュレーション計算はDomainへ置き、SwiftUIから分離する。

### Persistence

- SwiftDataとDomain／画面表示の境界を担当する。
- Previewやテストでは、メモリ内ストアまたはテスト用実装へ切り替えられる形にする。

## 初期データモデル

保存作品は、概念上次の情報を持つ。

```swift
struct KumihimoProject {
    var id: UUID
    var name: String
    var selectedBraidPresetID: BraidPresetID?
    var threadCount: Int
    var threadAssignments: [ThreadAssignment]
    var thumbnailData: Data?
    var createdAt: Date
    var updatedAt: Date
}
```

これは概念モデルであり、そのまま永続化型にすることを強制しない。`BraidPresetID`、`ThreadAssignment`、`ThreadColor` の具体表現は後続の技術検証で確定する。

`selectedBraidPresetID` は任意である。組み方を選ばず、糸本数と色配置だけの作品も有効な保存データとして扱う。

`ThreadAssignment` は少なくとも、天板上で変わらない位置番号と色IDを持つ。配列の添字だけを永続的な位置識別子として扱わない。

### データ上の不変条件

- `id` は作品作成時に生成し、その後変更しない。
- `name` は空白文字だけにしない。
- `threadCount` は正の値とする。
- `threadAssignments` の有効な位置数は `threadCount` と一致する。
- `selectedBraidPresetID` がある場合は、そのプリセットが現在の糸本数に対応している。
- `updatedAt` は作品内容の保存時に更新する。
- 色は表示名だけでなく、再現可能な色値を保持する。

## 編集セッションと保存

作品編集画面は、SwiftDataの永続化モデルをViewから直接編集しない。画面を開いた時点の内容から `ProjectDraft` を作り、保存操作が完了したときだけ永続ストアへ反映する。

これにより、次を区別する。

- 新規保存: 新しいIDで作品を作成する。
- 上書き保存: 開いている作品のIDを維持して内容と `updatedAt` を更新する。
- 名前をつけて保存: 新しいIDと作成日時で複製し、元作品を変更しない。

名前をつけて保存した後は、新しく作成した作品を現在の編集対象とする。

## 色カタログ

- UIは任意色を作るカラーピッカーではなく、`ThreadColorCatalog` が提供する有限の色一覧を使う。
- 色は安定したID、表示名、再現用の色値、任意の商品コードを持てる構造にする。
- 初期の仮カタログと、将来の商品色カタログを差し替え可能にする。
- 永続データには表示順ではなく安定した色IDを保存する。

## 組紐台の俯瞰図

- 最初の表現は、円形の天板、中央の穴、外周から中央へ伸びる糸に限定する。
- 糸の位置は12時方向を基準に時計回りで安定して割り当てる。
- 描画の座標計算とタップ判定をView本体から分離し、糸本数に応じて等間隔に配置する。
- 見た目の糸が細くても、操作用のタップ領域は最低44×44ポイントを確保する。

## シミュレーション境界

シミュレーション機能は、入力と結果の境界を次のように扱う。

```text
入力: 糸本数 + 位置ごとの色ID + 組み方プリセット
出力: 安定した結果ID + 表示名 + 手順検証用の糸経路 + 完成表面パターン + 2Dサムネイル表現
```

プリセット一覧と計算処理はUIから分離する。ユーザーが保存した組み方を将来追加できるよう、UIは組み方の出所を固定しない。ただし初期実装ではアプリ内蔵プリセットだけを対象とする。

最初のプリセットは16本の丸源氏とする。資料から読み取った1周期を、上下の外側2本の交換、左右の外側2本の交換として純粋なDomain計算にする。順序付き移動イベントと糸位置ごとの連続した3D経路は、組み手順を検証するDomain結果として保持し、完成外観の描画には直接使用しない。

丸源氏の完成外観は、実物3例と照合した位置別配色から64枚の正規化表面パッチへの対応を別のDomain結果として生成する。2Dサムネイルと3D詳細はこの表面パターンを共通の正本とし、3Dでは単一の円筒状表面メッシュへ変換する。これにより、手順検証の自由空間内の糸経路と、締められた完成表面を区別する。

3D詳細はiOS 17で利用できるRealityKitの非AR `ARView` をSwiftUIへ埋め込む。カメラ映像やARセッションは使用せず、アプリ内で生成したチューブ状メッシュを表示する。完成プレビューでは端面を生成せず、同じ周期の表面メッシュを長手方向へ反復配置して、表示領域の外まで続く長尺の組紐として見せる。操作は長軸回転、ピンチ拡大縮小、ダブルタップと画面上のボタンによるリセットに限定し、端面が見える長軸の傾斜は行わない。

## 適応レイアウト

- アプリターゲットはiPhoneとiPadをネイティブにサポートする。
- iPhoneのコンパクト幅では、従来の1列スクロールと `NavigationStack` を維持する。
- 十分な横幅がある場合、作品編集画面は配色設定とシミュレーション結果を左右へ分け、3Dを右側の主要コンテンツとして表示できる構成にする。
- iPadという端末種別だけで分岐せず、Split View、Stage Manager、画面回転、Dynamic Typeを含む実際の利用可能幅に応じて配置を切り替える。
- 狭いiPadウインドウではiPhone相当の1列構成へ安全に戻す。

初期の3D形状は、実物3例との照合で確認した配色傾向を観察するための技術プレビューである。糸の厳密な上下関係、張力、締め具合、断面形状はまだ物理シミュレーションしないため、UI上で照合済みの範囲と未検証事項を明示する。

実際の組紐結果に見える根拠のない装飾画像を、シミュレーション結果として本番表示しない。検証途中のアルゴリズムを表示するときは、根拠と限界を仕様に記録し、画面上でも試作であることを明示する。

## ナビゲーション

初期画面をアプリのルートとし、次の遷移を想定する。

```text
ホーム
├── 新しく編む → 作品編集（未保存の新規案）
└── 保存作品   → 作品編集（既存作品の詳細）
```

画面遷移時は、可能な限り作品全体ではなく作品IDまたは編集用状態を渡す。戻る操作はiOS標準の挙動を維持する。

## サムネイル

- サムネイルは作品の派生データとして扱う。
- 元の糸配置や組み方を正本とし、サムネイルを唯一のデータ源にしない。
- 生成前または復元不能の場合はプレースホルダーを表示する。
- 起動画面の初期実装では、実レンダリング処理を作らずプレースホルダーでよい。

## エラー処理

- 保存データの読み込み失敗を、作品が0件である状態と混同しない。
- ユーザーが対処できるエラーには、短い説明と再試行手段を用意する。
- 開発者向け詳細をそのまま画面に表示しない。

## テスト方針

優先して自動テストする対象は次のとおり。

- 保存作品の更新日時順の並べ替え
- 作品の追加、更新、削除
- データモデルの不変条件
- シミュレーション計算の既知入力と期待出力
- ナビゲーションに渡す作品ID

UIテストでは、主要なユーザーフローを少数に絞る。

1. 空状態から新規作成を開始できる。
2. 保存作品を開ける。
3. 作品を確認付きで削除できる。

## 遮蔽マップをマテリアルのどのスロットへ与えるか（2026-09-05）

組紐の表面の谷の陰は、糸ごとに生成した遮蔽マップで描く。このマップを与える先には2つある。

- `baseColor` へ色として掛ける — **直接光**を弱める。
- `ambientOcclusion` スロットへ与える — **環境光**を弱める。

**両方へ与えるのが遮蔽マップ本来の使い方であり、明暗の付き方が大きく変わる。** Task 007E
段階4a の実測では、平源氏の長手方向の輝度変調が `baseColor` のみで 0.463、両方で 0.618
だった（資料の完成写真は 0.670〜0.884）。定数は一切変えていない。

**非対称は Task 005J 段階1（2026-09-06）で閉じた。両方とも両スロットへ与える。**

- 平源氏（Task 007E 段階4a 以降）: 0.463 → 0.618。
- 丸源氏（Task 005J 段階1 以降）: 0.489 → 0.617。資料の丸源氏は 0.738〜0.814。

### 訂正: 丸源氏の「0.605」は単色の値ではなかった（2026-09-06）

ここには当初「丸源氏は同じ手順で測ると 0.605」と書いてあった。**この数字は手順を満たして
いない。** 測定手順書は「単色の行」を要求しているのに、0.605 は青と桃の2色の fixture 1 で
取られていた。行の中で色が替わるぶんだけ値が上がる。単色フィクスチャで測り直すと **0.489**
である。

**間違えた理由**: 平源氏では主値の fixture B がたまたま面全体で単色だったため、「そのとき
手元にあったフィクスチャで測る」ことと「単色の行で測る」ことが一致していた。丸源氏へ数字を
1つ並べたとき、この一致が偶然だったことに誰も気づかなかった。**手順が要求する条件は、
フィクスチャを替えるたびに満たされているか確かめること。**

なお Task 007E の判断はこれで動かない。平源氏の合格条件は「下限 0.5 と目視」であり、
0.605 は参考として並べただけで判定には使っていない。

### この指標が掛けられない帯

変調 `(p95 − p5) / p95` は p95 で割るので、**p95 が小さい帯では発散する。** 黒や紺のように
極端に暗い帯は、分母が小さいぶんだけ値が跳ね、明るい帯と並べて比べられない。単色で続くのが
そういう帯しかない資料は、この手順では測れない。除外して理由を書くこと。

Task 005J 段階1 で bookA p94（丸源氏の完成写真）を外したのがこれである。長手方向に1色で
続くのは黒の縁取りだけで、山形の側は白・橙・桃が交互に来るため単色の帯が取れない。

手順の正本は `docs/measurement-procedures.md`。生データは
`.build/task007e-screenshots/` と `.build/task005j-screenshots/` にあるが、**`.build/` は
git の管理外なので、判断に効く事実は正本の側へ写すこと。**

## 畝の高さと模様の縦横比は、実物写真からは分離できない（2026-09-06）

Task 005J 段階2b で分かった。**写真から測れるのは「見かけの山形密度」という両者の組み合わせ
1つだけであり、片方を動かせばもう片方も動かさないと写真に合わなくなる。**

見かけの密度 = 見かけの紐幅 ÷ 山形のピッチ。山形のピッチは `patternAspectRatio` だけで
決まる。見かけの紐幅は `crestHeightRatio` で変わる — 畝を上げれば紐は太る。**幾何に触れて
いなくても、畝を動かせば写真と比べる量が動く。**

### 紐幅の取り方（この数字を書くときは必ず添えること）

見かけの密度は**何を紐幅とするかで変わる。基準を書かない数字は使えない。** 丸源氏では
候補が3つあり、値がこれだけ違う（`patternAspectRatio` 0.65、頂 0.12）:

  公称（平均面）              2 × 半径                              1.96
  **畝の稜線での外径**        2 × 半径 × (1 − 谷の深さ + 頂)        **2.14**  ← これを使う
  メッシュの最大半径          交差で糸が乗り上げるぶんを含む        2.17

**採るのは畝の稜線での外径である。写真が測っているのは紐の外形の幅だからである。**
レンダーの輪郭を実測すると稜線の予測に対して −1.2〜−1.6% で一定して追随し（差は亜画素の
辺の取り方）、メッシュの最大半径に対しては −3.3〜−5.4% とずれ、しかも**ずれが頂とともに
広がる。** 交差で糸が乗り上げる分は局所の瘤であって、輪郭を決めていない。

### 丸源氏の値（紐幅 = 畝の稜線での外径、実物写真は 1.8〜2.15）

  頂 0.12（現状）  見かけの密度 2.14  帯の上端ぎりぎり
  頂 0.24          見かけの密度 2.37  帯の外
  頂 0.353         見かけの密度 2.59  帯の外

**0.12 が帯の内側にあることを据え置きの根拠にしないこと。** 2.14 は上端 2.15 との差が 0.5%
しかなく、紐幅の取り方を1つずらせば（メッシュ最大なら 2.17）外側へ出る。**内か外かは
決められない。**

**据え置きの根拠は「0.24 と 0.35 は明確に帯の外で、0.12 だけが桁違いに帯へ近い」ことである。**
上端からの距離は 0.12 が 0.5%、0.24 が 10%、0.353 が 20% である。

0.353 は「平源氏で決めた 0.45 糸幅ぶんを丸源氏の半径比へ直した値」（0.45 × π / 4）である。
**物理はこれを指すが、写真は反対を指す。** 0.353 を入れて写真へ戻すには
`patternAspectRatio` を 0.75 付近へ動かす必要があり、それは Task 005I を開き直すことになる。

### 絡まりの強さは断面の形で決まる

同じ「頂 0.12 → 0.45」でも、**見かけの紐幅の増え方が組によって違う。**

  丸源氏（丸い断面）  紐幅 +21%   畝は半径へ、つまり幅へ直に効く
  平源氏（平たい断面）紐幅 +4.5%  畝は厚みと幅へ散り、幅への取り分が小さい

**これが、丸源氏で絡まりが効き、平源氏で効かない理由である。** 平源氏は頂を 0.12 から 0.45
へ動かしても、見かけのピッチ÷紐幅が 0.3665 → 0.358 と 2.3% しか動かず、資料
（0.332 / 0.351 / 0.382 / 0.422）の中に留まった。丸源氏は同じ操作で写真の帯から出る。

**Task 008 以降の丸い組み方 — 八つ金剛組・江戸八つ組・八つ瀬組・唐八つ組・江戸源氏組 — は
すべて絡まりが強く効く側である。** 断面が丸いか丸に近い組では、畝と縦横比を写真だけで
別々に決めることはできない。**最初からそのつもりで進めること。**（方丈組は断面を確かめて
から判断する。）

**根拠が物理の1本だけで、写真の1本が反対を指しているので、どちらも動かさない。**
`docs/tasks/016-braid-physics-feasibility.md` の結論が出るまで、丸源氏の
`crestHeightRatio` と `patternAspectRatio` のどちらも動かさないこと。**物理から解けば両方が
独立に出るので、この絡まりは自然に解ける。** 016 が成立するかの判断材料の1つでもある。

### 番人

`theChevronDensityFollowsTheDeclaredAspectAtAnySize` は当初これを検出しなかった。公称半径
（`mesh.baseRadius`、平均面）で計算していたため、畝をいくつにしても値が動かなかったからで
ある。**写真が測っているのは外側のシルエットなので、テストもそれで測る**よう
`mesh.visibleWidth` へ直した。頂 0.12 で通り、0.24 と 0.35 で落ちることを確認済み。

`visibleWidth` は上で採った**畝の稜線での外径**である。`strandRadius` を目の途中
（交差の重みが 0、断面が稜線の上）で読むので、畝の作り方を変えればここも追随する。

**経緯**: これは一度メッシュの最大半径で書かれていた。交差で糸が乗り上げる分を含むぶん
大きく、帯の上端を 3.4% 広げて 1.5〜2.3 として辻褄を合わせていた。**その 3.4% は頂 0.12 で
較正した値で、頂 0.35 では 5.4% ずれる。** 未検証の仮定を定数で凍らせた形だったので、定義を
稜線での外径へ揃え、帯は Task 005I 本来の 1.5〜2.2 に戻した（2026-09-06 解消）。

### 両方の組で「外径」は稜線での外径である

  丸源氏  `MaruGenjiSurfaceMeshData.crestRadius` = 半径 × (1 − 谷の深さ + 頂)
  平源氏  外側の比 `(w/t + 頂)/(1 + 頂)` = 2.611。半厚を1として 外側の半幅 3.786 / 半厚 1.45

**平源氏はもともとこの定義である。** 平源氏の `crossingRelief` は頂を超えないので、
メッシュの最大＝稜線での外形であり、丸源氏のような乗り上げ分の差が生じない。丸源氏だけが
`overCrossingLift` を持つため、そこだけ2つの値が割れていた。

### 測るときの落とし穴: 遠近法

レンダーのスクリーンショットから見かけの密度を読むと、**14% ほど低く出る。** 山形は手前の
面にあってカメラに近く拡大されるのに対し、紐幅は最も広いところ＝軸と同じ奥行きで測るため
である。倍率は `カメラ距離 / (カメラ距離 − 外半径)`（4.4 / (4.4 − 0.52) = 1.135）。

Task 005J 段階2b は当初この補正を欠いており、1.87 / 2.06 / 2.21 と報告した。補正すると
2.12 / 2.37 / 2.58 で、**幾何から直接出した 2.14 / 2.37 / 2.59（紐幅 = 畝の稜線での外径）と
0.6% で一致する。** 2つの独立な経路が同じ値を返したので、この組を正本とする。
**スクリーンショットから幾何量を読むときは、必ず幾何と突き合わせること。**

## 平らな面では fill の強さで谷は戻らない（2026-09-05）

「fill が強すぎて谷の陰が消えている」という見立ては誤りだった。Task 007E 段階4a で fill を
520 / 260 / 0 と振って測った変調は 0.463 / 0.466 / 0.472 でほとんど動かない。fill の向き
`(-1.5, -1, 2)` が平らな面へほぼ正面から当たるためである。**平らな braid の谷を深くするのは

## 2つの組の畝の高さは揃っていない（2026-09-05）

**単位が違ううえ、片方は測った値で片方は測っていない値である。** 以前は平源氏側のテストが

だけで、削除した。糸1本あたりに直すと平源氏は丸源氏のおよそ3倍盛り上がる。

（`docs/tasks/005j-maru-genji-ambient-occlusion.md`）。**測る前に揃えないこと。**

### 測り方（両方に使える）

紐のシルエットの上辺を、輝度が背景と紐の中間値を下向きに横切る点として亜画素で求め、
1手のピッチ2つぶんの移動平均を引いた残差の σ を、ピッチに対する比で表す。

**残差の自己相関でさざ波の周期を求め、1手のピッチと一致することを必ず確認する。**
一致しなければ測っているのは糸のけばであって形ではない。この確認が無いと、bookB p23 の
白い縁糸（周期 r=0.16、糸の直径の1.3倍という物理的にありえない値になる）を資料として
採ってしまう。

平源氏のレンダーでの較正は σ(%) = 9.55 × 頂（頂 0.12 / 0.24 / 0.48 で線形を確認）。

**較正は組ごとに取り直すこと。丸源氏は直線ですらない**（Task 005J 段階2、頂 0.00〜0.48 の
8点）。

  丸源氏  σ(%) = 17.31 × 頂^0.752（残差 0.044、頂 0 で σ 0.02%）

丸い紐のシルエットは接線の包絡なので、畝が高くなるほど隣の畝の谷が隠れて飽和する。平らな
面にはこの飽和が無い。**平源氏の式を引き写していたら大きく外していた。**

丸源氏の端の波形の周期は 1手の山形の 4/9（レンダーで 141px に対し 62px、頂によらず一定）。
平源氏では 1手そのものだった。**組が変われば周期も変わる。**

### シルエット法は丸い紐には使えない（Task 005J 段階2、2026-09-06）

「丸源氏の良い写真が無かった」ではない。**この測り方が丸い紐に向かない。** Task 005J で
実際に試して、根拠が3つ揃った。

1. **実物の外周が滑らかで、畝の列に見えない。** 手元の4枚とも、拡大しても縁は1本の滑らかな
   紐である。**丸源氏には糸が折り返す縁が無く、糸は斜めにシルエットを横切るだけなので、
   滑らかなのが正しい可能性が高い。**
2. **シルエットの特徴が目と1対1に対応しない。** レンダーの端の波形の周期は1手ではなく
   1手の 4/9（141px に対し 62px）。平源氏では1手そのものだった。
3. **較正が飽和する。** 丸い紐のシルエットは接線の包絡なので、畝が高くなるほど隣の畝の谷が
   隠れる。頂を2倍にしても σ は2倍にならない。

**平源氏のシルエット法は、縁で糸が折り返す平たい紐だから成立した道具である。**
Task 008 以降の丸い組み方（八つ金剛・江戸八つ・八つ瀬・唐八つ・江戸源氏・方丈）で畝を
決めるときは、この手順を最初から選択肢に入れず、別の観測量を先に探すこと。

そして測ってしまった場合の危うさも記録しておく。**周期を確認しなければ、資料は現在の
0.12 を追認する。** 各資料の σ を較正へ通すと頂 0.045〜0.193 が返り、0.12 はそのまん中に
落ちる。測っているのは糸のけばと紙・木目のざらつきである。**周期の確認は形式ではなく、
これが唯一の歯止めである。**

## 断面は巡回列である。畳み方は導出であって入力ではない（2026-09-06、Task 020 段階1）

## 向きの取り決め: 「上から見て」は組み点から紐を見下ろす向き（2026-09-11、Task 032）

## 正本の読み方（作者の指示）: bookC の1手は1本である（2026-09-07、Task 020 積1）

## 組み台の力学（作者の前提）: 面に見えるのは、そこに留まっている糸である（2026-09-07、Task 021b-1）

**これは作者が置いた前提であり、この repo での正本である。** Task 021a（到着点どうしを斜めの
直線で結ぶ初期配置）が面で不合格になった原因はここにあった。

### 前提

- 各糸の端には玉（錘）が付いていて、丸台の鏡の縁に沿って、**自分の位置へ向けて外向きに引かれ
  続けている**。円状に外向きの張力。
- 組み上がっていく紐の端にも錘が付いていて、**下へ引かれ続けている**。
- したがって、**どの糸にも常に張力がかかっている**。ゆるんでぶら下がっている糸も、中央で遊んで
  いる糸も無い。**どの区間も張った直線。**

### 前提から出ること

1. **位置に留まっている糸は、外向きの張力で紐の表面のその角度に張り付いている。** 到着の長手
   座標から出発の長手座標まで、**表面に沿った縦の走り**。内側には入らない。「留まっている」は
   張ったままの意味であって、ゆるんでいるという意味ではない。
2. **運ばれる糸は、置かれた瞬間から新しい位置へ外向きに引かれている**ので、古い位置の表面から
   新しい位置の表面まで、**その時点の束の上面に押し付けられた張った直線**になる。渡った直後は
   最新層、次の手が積まれるごとに下の錘で押し込まれ、出来上がりでは**層座標 z の高さの直線**
   として残る（積み重ねの模型そのもの）。**渡りが表面に触れるのは両端だけで、中央で浮いている
   区間は無い。**
3. よって**表面のある角度に見えるのは、そこに留まっている糸だけ**。
   **面の模様 = 位置の占有履歴。**

## 組み上がりの解き方は準静的である（作者の決定）（2026-09-07、Task 022）

**これは作者の決定であり、この repo での正本である。**

> 揺れを見たいのではない。**動力学は要らない。** 糸は物体に沿って曲がったら、あとは剛体の
> ように動かなくてよい。

したがって Task 022 の模型には、**質量・重力・慣性・減衰・時間刻みが1つも無い。** 一手は
次の4つで、それだけである（`docs/tasks/022-braid-on-the-stand.md`）。

  運ぶ    指定の糸の自由部分を、他の全部の糸の上を通して新しい角度へ移す
  張る    両端を留めたまま糸をまっすぐにし、余りを縁側へ送る
  固定    束に取り込まれた区間を剛体として固定し、以後動かさない
  記録    各手の後の全カプセル中心を書き出す

**張った糸とは、両端のあいだで、他のすべての外を通る最短の道である。** 拘束は2つだけ——
太さ d のカプセルどうしが通り抜けないこと、隣り合う球の距離が d であること。**当たった糸の
上で曲がり、当たっていない区間は真っ直ぐになる。**

### Jolt は試した上で不採用（2026-09-07）

**理由: 要件が準静的になり、動力学の部品（質量比、慣性、減衰、時間刻み）が障害にしかならない
ため。要件が変われば再検討する。** Jolt の harness は `Scripts/task022/jolt/` に**動力学が要る
ときの起点**として残す（台の幾何、種、bookC の手の運び方はそのまま使える）。**Jolt のソースは
repo に置いていない。CMake の FetchContent がタグ固定で取ってくる。**

### 組み点の深さは錘の比で決まる

玉が糸を縁の外へ引き、吊りおもりが束を下へ引く。糸は束を出て上と外へ走り、穴の内側の丸めに
当たるので、真っ直ぐな区間はその丸めへの接線である。釣り合いは

    糸の本数 × 玉の重さ × sin(水平からの角度) ＝ 吊りおもりの重さ

**16本・玉 100 g・吊り 570 g で、組み点は鏡の上面から −1.658 d**（`Scripts/task022/stand.py`
の `braiding_point_depth`）。**束の半径に依るので、半径 2.546 d（円周の読み）で計算すると
−1.665 d になる。正しいのは正16角形の読みのほうで、−1.658 d である**（2026-09-07 に訂正）。

**これは「結び目が穴の口へ上がる」という 022-1 の動力学の観察と同じことを、2つの錘から一度
だけ解いたものである。以後は定数として記録する。**

### 束の周りに糸が立つ半径

**糸は束の周りに互いに接して立つ**ので、中心間距離は d、中心は1辺 d の正16角形の頂点であり、
半径は **d ÷ (2 sin(π/16)) = 2.5629 d** である。**周長を 16 d とする読み（半径 2.546 d）は、
隣どうしを 0.9938 d に置いてしまう**（何も起きないうちから 0.6% 食い込んでいる）。断面の
「周長＝糸16本」はこの正16角形の周長のことである。

**product code は半径を持っていない。** `BraidCrossSection` は**並び順だけ**で、寸法を1つも
持たない。「周長 16 d」の読みが数値に効いているのは**平源氏の断面比 3.3359 の導出**
（周長＝糸16本・厚み＝糸2本）と `HiraGenjiSurfaceMeshGenerator` の寸法であり、そこでは
**円周と正16角形の周長の差 0.7%** がそのまま乗る。**Task 022 は多角形の読みを使う。
既存の値は動かさない**（凍結中の生成器は Task 022-4 まで触らない）。

## 山は糸の半径から出る（作者の決定）（2026-09-08、Task 024）

**これは作者の決定であり、この repo での正本である。**

**糸の各位置（留まりの場所、交差点）の基準の高さに対して、別の糸がくぐる可能性のあるところ
では、越える糸を +d/2、くぐる糸を −d/2 だけ表面の法線方向にずらした山を作る。**
**山の形は弧でも直線（三角）でもよい。交差点での中心間距離はちょうど d になり、貫入は構成で
消える。solver は使わない。**

**裏付け**: **平源氏の膨らみの測定 0.45（輪郭、Task 007E）と 0.40〜0.50（物理の重なり）は
d/2 = 0.5 に一致する。** **これまで観測値として与えていた膨らみが、糸の直径から出る。**

**山の幅も d である**——中心から ±d/2 で最大、その外で 0 に戻す。**定数は d だけ。**

### 山の向きは面の法線で決める（追記、2026-09-08）

**山の向きは対の関係（どちらが上か）から決めない。糸が今いる面の外向き法線で決める。**
**白（基準面）を 0 とし、表の糸は +d、裏の糸は −d に既にずれている。山はそのずれている側へ
だけ膨らむ。実世界で重ね合わせの上下が逆になることは無い。**

**面は `BraidCrossSection` の畳みが各場所に与えている**（表／裏／縁。丸源氏は全部が外周で
法線は半径方向）。**糸が表の場所に動けば表、裏の場所に動けば裏。腹や芯を横切る渡りは 0
（膨らまない）。**

**平源氏の素の厚みは 2 d である**（追記、2026-09-08）——**表の縦糸は +d/2、裏は −d/2。
触れ合っている。3 d ではない。**

**横紐（腹を横切る渡り）は 0 の高さを、自分の Z（積み重ね模型の層）で通る。厚み方向に常設の
層は持たない。** **横紐が通るところだけ、表の縦糸は +d/2、裏は −d/2 押されて（山）、そこで
厚みが 3 d になる。それ以外は 2 d。**

**横紐どうしは厚み方向に重ならない。長手（Z）に並ぶ。** 積み重ね模型の**1列1サイクル ＝
縦糸の着地1層 ＋ 横糸の通過2層**のとおり、**横紐2本は Z で d 離れている**——
「表裏の交差｜横紐 A｜横紐 B｜裏表の交差」で**横紐が Z に 2 d を占める。**

**一つの区間に複数の山が付くときは、足さずに重ねる（各点で最大を採る）。打ち消しは起きない。**

**同じ場所を前後で引き継ぐ2本は、積み重ね模型のとおり、後から来た糸の到着層が前の糸の出発層の
一つ上である。端どうしは d 離れる。これは重なりではなく層の段差である。**
