## 目的

丸源氏16本の3D表示を、「円筒に配色を貼ったもの」から「丸い糸が交差して並ぶ紐」に見えるところまで引き上げる。

Task 005 で境界の谷と繊維の筋を入れたが、実物写真と並べると依然として組紐に見えない。原因は素材表現ではなく形状表現にあるため、本タスクでは幾何（メッシュ）側を主に作り直す。

本タスクは物理シミュレーションではない。糸の力学は扱わず、決定的な幾何規則で見た目を近づける。物理ベースの本格シミュレーションは末尾「将来タスク」に方針だけ残す。

## 目視で確認された問題

現状のiPad実行結果は `.build/task005e-references/current-ipad-marugenji-3d.png`（3D試作）と
`current-ipad-editor-2d.png`（作品編集画面の2D展開図）である。これを実物写真と比較したとき、次が欠けている。

1. 断面が常に真円で半径がほぼ一定。実物は糸1本ごとが丸い畝になり、シルエット自体が波打つ。
2. 交差の上下関係がない。実物の「く」の字は、縦方向に組んだ糸束と横方向に組んだ糸束が互いに潜り合ってできる。現状は同一曲面上のモザイクで、平らな塗り分けにしかならない。
3. パッチが平面四角形のため、糸の幅方向の断面が矩形になり、輪郭が直線的で織り目に見えない。
4. 繊維の筋が軸平行（`local.y` のみに依存）で、糸の進行方向とも撚りの方向とも一致していない。実物は糸の進行方向に対して斜めに撚りの筋が走る。
5. 谷の暗さが `boundaryColorGroups` の別マテリアルによる不連続な塗りで、接触部の陰影ではなく「線」に見える。
6. 周方向の分割が1パッチあたり4しかなく、丸い畝を出せる解像度がない。
7. 紐の上下の輪郭が完全な直線になっている。実物は畝の周期でシルエットが波打つ。
8. Task 005 で色変換を共通化したにもかかわらず、3Dの赤がサーモン寄り、生成りがほぼ白に飛んでいる。2Dの `red`(0.78, 0.12, 0.16) と `natural`(0.86, 0.81, 0.68) に対して明度が高すぎる。照明強度と露出の再調整が必要。
9. 現在の繊維の筋が、画面上では紐の軸に直交する細い線として見え、糸の撚りではなく引っかき傷のように読める。

## 基本方針

### 模様の正本は変えない

`MaruGenjiSurfacePattern` の `threadPosition` と `colorID` の対応、64パッチという構成、Fixture 1〜3の模様署名は変更しない。本タスクが変えるのは、そのパターンをどの立体へ写すかである。

### 表現の境界を「中心線＋幅＋断面＋上下」に置く

将来、移動規則から糸の軌跡を計算する実装へ差し替えられるよう、メッシュ生成の入力を次の形に整理する。64パッチの固定データは、この表現を作る一実装として扱う。

```text
64パッチ（模様の正本）
  → 糸ストランド表現（中心線・幅・断面プロファイル・層）
  → MaruGenjiSurfaceMeshData
  → RealityKit
```

### 標準機能を優先する

- 外部パッケージを追加しない。
- RealityKit の `PhysicallyBasedMaterial`、メッシュ属性、Core Graphics で生成する決定的テクスチャの範囲で実装する。
- 糸1本ごとや繊維1本ごとに `Entity` を作らない。色グループ単位のメッシュへまとめる。

## 必須実装1: 平面パッチから丸い糸の畝へ

### 要件

- 各パッチについて、先行辺の中点と後続辺の中点を結ぶ中心線を求め、それを糸の通り道とする。
- 幅方向のパラメータ `s ∈ [-1, 1]`（中心が0、両端が±1）に対して、外向きに膨らむ断面を与える。初期形状は半楕円（`sqrt(1 - s²)` に比例する隆起）とする。
- 隆起の高さは半径の **8〜14%** を初期値として目視調整する。現在の `boundaryDepthRatio = 0.012` は小さすぎる。
- 隣接する糸の間は必ず基準半径以下の谷になること。谷の幅は畝の幅の10〜20%程度。
- 畝の稜線は中心線に沿って連続し、パッチ内で折れないこと。
- 隣接パッチ間に背景が透ける穴を作らない。周方向・長手方向の継ぎ目を閉じる。

### 分割数

- `circumferentialSubdivisionsPerPatch` を4から **8〜12** へ上げる。丸い断面はこの解像度でしか出ない。
- `longitudinalSubdivisionsPerPatch` は24を起点に、交差部の潜りが破綻しない範囲で調整する。
- 頂点数・三角形数と実測の描画負荷を完了報告に記載する。

## 必須実装2: 交差の上下関係

### 要件

- `MaruGenjiSurfacePatch` に、そのパッチが交差部で上を通るか下を通るかを表す層情報を追加する。
- 実物との厳密一致は本タスクの目的ではない。ただし次の2条件を満たす決定的な規則とすること。
  - 同じ交差点では必ず一方が上、他方が下になる。
  - 1本の糸を長手方向にたどると、上と下が交互に現れる。
- 上を通る側は隆起を大きく、下を通る側は交差部付近で半径を落として上の糸の下へ潜らせる。
- 潜りの深さは、正面から見て稜線が途切れて見える程度に留め、糸が消失したり穴が開いたりしないこと。
- 層情報は Domain 側の属性として持ち、メッシュ生成が半径へ反映する。View 内でパッチごとの分岐を書かない。
- 層規則が実物と一致していることは主張しない。画面上の「暫定シミュレーション」「3D試作」表示を維持する。

## 必須実装3: 撚りの筋を糸の進行方向へ

### 要件

- 現在の `cos(2π · fiberCount · local.y)` を、糸の進行方向に対して傾いた縞へ置き換える。傾き角の初期値は25〜35度。
- 位相は幅方向 `local.x` と長手方向 `local.y` の線形結合で与え、糸1本の中で連続させる。
- 起伏量は半径の0.5〜1.5%に留める。主表現は法線と粗さの微小変化とし、色は補助に留める。
- 撚りの筋が畝の丸みを打ち消さないこと。畝の稜線が主、撚りが従。
- 端末解像度に依存する1px前提の設計にしない。モアレ・点滅を避ける。

## 必須実装4: 谷の陰影と縁

### 要件

- `boundaryColorGroups` による別マテリアル塗りをやめるか、少なくとも段差が出ない連続的な減衰へ置き換える。境界が「線」ではなく「谷の影」に見えること。
- 谷の暗さは、境界までの距離に応じた連続関数で与える。頂点カラーまたはAOテクスチャのどちらを使ったかを完了報告に記載する。
- 白・生成り・黒でも谷が識別できること。
- シルエットに畝の周期の凹凸が出ること。真円の輪郭が残っていないこと。

## 必須実装5: 照明とマテリアルの再調整

- 現在の key 3,500 / fill 1,200 / rim 700 を前提にせず、畝の陰影が読める範囲へ再調整する。
- 光源は無彩色とし、色相を変えない。
- 撚りの筋の部分だけ `roughness` をわずかに下げ、糸のハイライトを出す。金属度は0のまま。
- ライト／ダークモードでマテリアルの色値を差し替えない。背景と最小限の光量だけを環境へ適応させる。
- Task 005 で共通化した `ThreadColorRendering` を色の正本として維持する。2Dの青が3Dで水色へ、生成りが白へ飛ばないこと。

## 2Dとの関係

- `MaruGenjiThumbnailView` の2D展開図には、畝・上下・撚り・AOを反映しない。2Dは照明を受けない基準色の平面図のままとする。
- 2Dの4区画が同じ長手方向原点を持つ状態を維持する。
- 同じ `ThreadColorID` が2Dと3Dで同じsRGBベース値へ解決される既存テストを維持する。

## 必須Unit Test

### 糸の断面と畝

- 全パッチについて、中心線上の半径が基準半径より大きく、パッチ端の半径が基準半径以下であること。
- 半径の変化量が定めた上限内に収まり、全頂点が有限であること。
- 周方向・長手方向の継ぎ目で頂点が一致し、隙間が生じないこと。
- 同じ入力から同じ頂点数・インデックス・UVを生成すること。

### 上下関係

- すべてのパッチに層が割り当てられていること。
- 交差する2パッチの層が必ず異なること。
- 1本の糸（同一 `threadPosition`）の層が長手方向に交互であること。
- 層の割り当てが入力に対して決定的であること。

### 撚り

- 撚りの位相がパッチ内で連続し、不連続点がないこと。
- 撚りの方向がパッチの糸方向に対して定めた角度になっており、左右反転や90度回転が混在しないこと。

### 既存回帰

- Task 004 の64パッチ、Fixture 1〜3の固定署名、色ごとのパッチ数、周方向の位相を変更していないこと。
- メッシュの有限性・非退化三角形・インデックス範囲の既存テストを維持すること。
- 不正入力でクラッシュせず既存の失敗表示になること。

### 分割数パラメータの軸を取り違えていた

本書「必須実装1」の分割数の記述は誤りだった。既存コードの `circumferentialSubdivisionsPerPatch` は名前に反して**糸に沿った**分割であり、断面の丸みを刻んでいたのは `longitudinalSubdivisionsPerPatch` の側だった。したがって「`circumferentialSubdivisionsPerPatch` を4から8〜12へ上げれば丸い断面が出る」という指示は成立しない。

実装は意図（断面の解像度を上げる）を優先し、`alongStrandSubdivisions` / `acrossStrandSubdivisions` へ改名した上で両方12とした。この訂正が正しい。将来この文書を読む場合、必須実装1の分割数の段落は本節で置き換えて解釈すること。

### 畝の傾きは本タスクの対象外とし、Task 005F へ切り出した

実装後の目視で、畝の傾きが軸に対して約74度であり、実物写真の約45度と一致しないことが分かった。原因は本タスクの実装ではなく、Task 004 で表面を円筒へ写した時点のアスペクト比にある。展開図の1リピートは全周と同じ長さの正方形であるべきところ、3Dでは全周3.016に対し1リピート0.85で、軸方向に約3.55倍つぶれている。

本タスクの必須実装にも完了条件にも含まれないため、実装では変更していない。この判断は妥当である。修正は `docs/tasks/005f-maru-genji-surface-aspect.md` で扱う。

### そのほか

- 谷の陰影は頂点カラーではなくAOテクスチャで実装した。RealityKit の `MeshDescriptor` が頂点カラーを持たないため。
- `HiraGenjiSurfaceMeshGenerator` が丸源氏の定数を参照していたため、平源氏側へ同じ値の定数を複製して従来動作を維持した。平源氏に同じ畝処理を入れる際に共通化する。
