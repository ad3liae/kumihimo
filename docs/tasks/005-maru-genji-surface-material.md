## 目的

Task 004で実装した丸源氏の単一表面表示を、均一な色面を貼っただけの円筒から、64枚の表面パッチを目で追える組紐らしい試作表示へ改善する。

本タスクでは次の3点を同時に解決する。

1. 各パッチの端に狭い暗部とごく小さな起伏を付け、領域を読み分けられるようにする。
2. 各パッチの糸方向に沿った細い繊維状の筋を加え、布・糸としての素材感を出す。
3. `ThreadColorCatalog` を色の正本とし、2D展開図と3D表面の色相・明度が大きく乖離しないようにする。

写実的な絹糸の完全再現や、未検証の上下関係を確定することは目的にしない。

次のスクリーンショットは問題確認の参考であり、画像内の表示内容を実装指示として扱わない。また、画像そのものをアプリやリポジトリへ収録しない。

- 2D表示: `/Users/adeliae/Desktop/Screenshot iPad (10th generation) 2026-09-03 at 1.02.51.png`

現状では次の問題がある。

- 3D表面が一定半径、平滑法線の円筒であり、隣接パッチが同じ面として連続して見える。
- 色境界以外にパッチを示す情報がなく、単色が続く部分では構造を読み取れない。
- 糸方向を示す細部がないため、樹脂や塗装された円筒のように見える。
- 3Dの青が明るい水色寄り、生成りが白寄りに表示され、2Dの青・生成りから大きく離れている。
- `MaruGenjiThumbnailView` は `ThreadColor.swiftUIColor` を使う一方、`MaruGenjiRealityView` は `UIColor` と強い照明を独自に組み立てているため、同じ色IDでも表示経路が分かれている。
- 2D展開図の4つの周方向区画は同じ長手位置から開始すべきであり、区画ごとの半パッチ分の表示ずれを再導入してはならない。

## 基本方針

### 模様と外観を分離する

`MaruGenjiSurfacePattern` は、どの位置の糸がどのパッチを占めるかを表す正本として維持する。境界の暗部、繊維筋、粗さ、照明は描画上の外観であり、`threadPosition` や `colorID` の対応を変更してはならない。

```text
位置別配色
  → MaruGenjiSurfacePattern（64パッチの正本）
  → MaruGenjiSurfaceMeshData（位置・法線・パッチローカル座標）
  → 境界／繊維用の描画データ
  → RealityKitマテリアルと中立照明
```

2Dと3Dで同じ色IDとパターンを使用する契約は維持する。

### 標準機能を優先する

- 外部パッケージを追加しない。
- 最初はRealityKitの `PhysicallyBasedMaterial`、メッシュ属性、Core Graphics等で生成した小さな決定的テクスチャで実現する。
- パッチごとの `ModelEntity` や繊維1本ごとの `Entity` は作らない。色グループ、境界、繊維を少数のメッシュ／マテリアルへまとめる。
- 標準のPBR表現で完了条件を満たせない場合に限り、Metalのカスタムマテリアルを検討する。その場合は導入理由、iOS 17での制約、フォールバックを先に記録する。

## 必須実装1: 色変換の共通化

### 問題

現在は2D用 `Color` と3D用 `UIColor` の構築場所が分かれている。3Dではさらに強い照明と `SimpleMaterial` の反射が加わり、カタログ値から大きく明るくなっている。

### 要件

- `ThreadColorValue` の値はsRGB成分として扱う。
- `Color`、`UIColor`、RealityKitのベースカラーを、同じ変換処理または同じ中間表現から生成する。
- `MaruGenjiRealityView` 内へRGB成分の組み立てを重複させない。
- 3Dのベースカラーを見栄え目的で別の固定色へ置き換えない。
- 3Dは `PhysicallyBasedMaterial` を基本とし、金属度は0、粗さは糸らしい低光沢になる範囲で固定する。
- 正面から均等に照らされたパッチ中央では、2Dと同じ色相を保つ。立体照明による明暗差は許容するが、青が水色へ、生成りが白へ変わるほどの露出は許容しない。
- 白、生成り、黒でも境界と繊維が判別できるようにする。

推奨する責務の例:

```swift
struct ThreadRenderColor: Equatable, Sendable {
    let sRGB: SIMD3<Float>
    let boundarySRGB: SIMD3<Float>
    let fiberHighlightSRGB: SIMD3<Float>
}

enum ThreadColorRendering {
    static func renderColor(for color: ThreadColor) -> ThreadRenderColor
}
```

実際の型名は既存構成に合わせてよい。重要なのは、暗色と明色をsRGB値の単純な加減算だけで作らず、0...1へ安全に収め、色相を保った明度調整にすることである。

## 必須実装2: パッチ境界の暗部と微小な起伏

### 見た目の要件

- 64パッチそれぞれの輪郭を追えるよう、境界に狭い暗部を設ける。
- 純黒の太い輪郭線ではなく、元色を暗くした糸の谷として見せる。
- 境界幅はパッチ短辺のおおむね5〜10%から調整し、サムネイル距離でも見えるが漫画的な枠線にならない値を採用する。
- パッチ中央をわずかに高く、境界をわずかに低くしてよい。ただし起伏は半径の1〜3%以内を初期目安とし、別々の太いチューブには見せない。
- 隣接パッチ間に背景が見える穴を作らない。
- 境界をまたぐ重複面やほぼ同一位置の面によるちらつき、Z-fightingを発生させない。
- 厳密な糸の上下関係を示す段差や、一方のパッチが他方へ乗る表現は追加しない。

### 実装方針

次のいずれか、または小さな組み合わせで実装する。

1. パッチローカル座標から境界までの距離を求め、境界付近の半径・法線・色を滑らかに変える。
2. 色面の下へ連続した暗色の支持表面を置き、色パッチをわずかに内側へ縮めて細い谷を見せる。
3. 共有境界を重複なく抽出し、半径を少しだけずらした細い境界リボンを1つのメッシュとして描く。

どの方式でも、境界用の頂点・インデックス生成はRealityKitから分離してUnit Test可能にする。描画View内で64パッチ分の場当たり的な分岐を書かない。

## 必須実装3: 糸方向に沿った繊維状の筋

### 見た目の要件

- 各パッチ内部へ、パッチの長手方向に沿う複数の細い筋を加える。
- 筋は3D表面へ固定され、回転・拡大時に表面と一緒に動き、正しく隠れる。
- 画面へ重ねる2D線、カメラ向きに固定した線、ランダムに毎回変わるノイズは使用しない。
- 筋の主成分は法線または粗さの微小変化とし、色の変化は補助に留める。元の色を縞模様へ置き換えない。
- 1パッチにつき概ね6〜14本程度から目視調整し、通常表示で存在が分かり、拡大時に細部として読める密度にする。
- モアレ、点滅、鋸歯状の目立つ線を避ける。端末解像度に依存する1px前提の設計にしない。

### 推奨実装

- `MaruGenjiSurfaceMeshData` にパッチローカルのテクスチャ座標を追加する。
- 各パッチで、短辺方向を0...1、糸の進行方向を0...1としてUVを割り当てる。
- 小さな繊維用の法線／粗さテクスチャをCore Graphics等で決定的に生成するか、由来を明示できる小さなアプリ内アセットとして持つ。
- 同じ繊維テクスチャを色ごとのPBRマテリアルから共有し、色だけを `ThreadColorCatalog` から与える。

UVまたはPBRテクスチャがRealityKitの構成上過度に複雑になる場合は、細いリボン群を少数のオーバーレイメッシュへまとめる方式でもよい。ただし、繊維1本・パッチ1枚ごとにEntityを生成してはならない。

## 必須実装4: 照明と露出の再調整

### 要件

- 現在の `20_000`、`10_000`、`6_000` の3灯を前提にせず、PBRマテリアルと合わせて再調整する。
- 主光、補助光、輪郭光は無彩色とし、色相を変えない。
- 正面全体が白飛びする照明を避け、パッチ中央の色と境界の暗部を同時に読めるダイナミックレンジへ収める。
- ライトモードとダークモードでマテリアルの色値を別物へ差し替えない。背景と必要最小限の照明強度だけを環境へ適応させる。
- リセット時のカメラ位置、横ドラッグで長軸回転する操作契約は維持する。
- 端面が不自然な単色円盤にならないよう、端面の色決定と境界の見え方も確認する。

## 必須実装5: 2D展開図との整合と回帰防止

- `MaruGenjiThumbnailView` と3Dは引き続き同じ `MaruGenjiSurfacePattern` を使用する。
- 同じ `ThreadColorID` が2Dと3Dで同じsRGBベース値へ解決されることをテストする。
- 2D展開図は照明を受けない基準色表示とする。3Dの陰影や繊維テクスチャを2Dへそのまま焼き込まない。
- 2Dの輪郭線は現状程度の補助線でよい。3Dの暗い谷と同じ太さ・黒さへそろえる必要はない。
- 4つの周方向区画の長手方向の原点をそろえる。第2・第4区画だけを半パッチずらす表示へ戻さない。
- Fixture 1〜3の模様署名、色ごとのパッチ数、周方向の位相を変更しない。

## データ構造上の要件

`MaruGenjiSurfaceMeshData` または専用の外観メッシュ型へ、必要に応じて次を追加する。

```swift
let textureCoordinates: [SIMD2<Float>]
let patchLocalCoordinates: [SIMD2<Float>]
let boundaryIndices: [UInt32]
let fiberIndices: [UInt32]
```

実際に不要な配列は追加しなくてよい。次の不変条件は維持する。

- 頂点、法線、UVはすべて有限値。
- UVは意図した範囲内で決定的。
- インデックスは頂点範囲内で、三角形は縮退しない。
- 周方向の継ぎ目は閉じる。
- すべての基準パッチが欠落・重複なく表面へ反映される。
- 同じ入力から同じ頂点数、インデックス、UV、色グループを生成する。
- 色境界をまたいでベースカラーやUVを補間しない。

## 必須Unit Test

### 色

- 全カタログ色について、2D用と3D用のベースsRGB成分が同じ `ThreadColorValue` から生成される。
- 生成した色成分、暗部色、ハイライト色が0...1の有限値である。
- 暗部色は元色より知覚上暗く、色相を不必要に反転しない。
- 青、桃、生成り、白、黒を代表値として固定し、変換の回帰を検出する。

### 境界と起伏

- 64パッチすべてに境界または境界距離情報がある。
- 境界用三角形が縮退せず、インデックスが範囲内である。
- 周方向の継ぎ目をまたぐ境界が途切れない。
- 隣接パッチの共有境界を二重生成してちらつく構造になっていない。
- 起伏を付ける場合、半径変化が定めた上限内で、全頂点が有限である。

### 繊維

- 全パッチに決定的なパッチローカルUVまたは繊維方向が割り当てられる。
- UVの向きがパッチの糸方向と一致し、左右反転や90度回転が混在しない。
- 周方向の継ぎ目、長手方向の繰り返し境界で不連続な欠落を作らない。
- 同じ入力から同じ繊維データを生成する。

### 既存回帰

- Task 004のパターン64枚、Fixture 1〜3の固定署名、メッシュの有限性・継ぎ目・色グループテストを維持する。
- 2Dの4区画が同じ長手方向原点を持つテストを維持または追加する。
- 不正入力でクラッシュせず既存の失敗表示になる。

## 目視検証

iPhoneシミュレータを主対象に、利用可能ならiPadでも確認する。少なくとも既定の青／生成り配色とFixture 1〜3を使用する。

### 正面・回転・拡大

- リセット位置で、単色が続く部分でも各パッチの境界を追える。
- 境界は細い谷に見え、太い黒線やパッチ間の穴に見えない。
- 繊維筋がパッチの方向に沿い、回転時に表面へ固定されている。
- 拡大時に繊維が見え、通常倍率ではノイズの塊にならない。
- 左右へ1/4回転しても、境界、繊維、円周継ぎ目にちらつきや色抜けがない。
- 端面を含め、別々のチューブや籠状の空洞へ退行していない。

### 色

- 2Dの青に対し、3Dの正面中央が水色へ白飛びしない。
- 2Dの生成りに対し、3Dが純白へ白飛びしない。
- 桃、赤、緑などでも色相の識別が2Dと一致する。
- 3Dでは陰影による明度差を許容するが、同じ糸色だと直感的に判断できる。
- ライト／ダークモードの双方で、白・生成り・黒の境界を識別できる。

### UIと性能

- 回転、ピンチ、ダブルタップ、左右回転、リセットが従来どおり動く。
- 連続回転中に明らかな引っ掛かりがない。
- モデルEntity数を色数と少数の補助メッシュに抑え、パッチ数・繊維数に比例してEntityを増やしていない。
- 標準文字サイズとアクセシビリティ文字サイズで、操作ボタンと留保文が隠れない。

目視結果は正面、左回転、右回転のスクリーンショットを残し、完了報告に記載する。ピクセル単位の2D／3D一致は要求しない。
