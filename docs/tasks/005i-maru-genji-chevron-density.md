## Task 005H から引き継ぐ判断

**周方向の列数を変更しない。** 表面パターンは Task 004 の8列×8行のままとする。

## 実装結果

- 状態: 完了（2026-09-04）

### 採用した縦横比: 0.65

`MaruGenjiSurfacePatternGenerator.patternAspectRatio` を 1.0 から **0.65** へ下げた。変更したのはこの1定数だけである。

出発点の 0.72 でレンダーして比較したところ、実物よりまだわずかに粗く見えた。**実物写真の読み方が2通りあり、その中間を採った。**

| 実物の読み方 | 紐幅あたりの山形 |
| --- | ---: |
| 目視で数える（タスク記載値） | 約1.8 |
| 正規化した帯から測る（下記） | 約2.15 |

| 試した縦横比 | 山形／幅（実測） | 1.8 との差 | 2.15 との差 |
| ---: | ---: | ---: | ---: |
| 1.00（Task 005F） | 1.25 | −31% | −42% |
| 0.72 | 1.75 | −3% | **−18%** |
| **0.65（採用）** | **1.93** | **+7%** | **−10%** |

0.72 は読み方1では合格、読み方2では外れる。0.65 はどちらでも ±15% に収まるため、写真の読み方が確定しなくても持ちこたえる値としてこれを採った。

### 実物の測り方と、その信頼性

タスクが指定する正規化（紐幅の4.5倍に切り出し、同じ高さへ拡大縮小）を行ったうえで、色に依存しない指標で糸の縦方向ピッチを測った。帯の上半分（糸が一方向に傾いている領域）の輝度の横方向勾配を列平均し、その周期をとる。色が変わっても糸の境界は必ず勾配に出るので、配色の違いに左右されない。

この推定器は、真値が解析的に分かっているレンダー2件で検証した。

| 対象 | 測定ピッチ | 真値 | 誤差 |
| --- | ---: | ---: | ---: |
| 縦横比 1.00 のレンダー | 0.3997 紐幅 | 0.3927 | +1.8% |
| 縦横比 0.65 のレンダー | 0.2588 紐幅 | 0.2551 | +1.4% |
| 実物写真 | 0.2321 紐幅 | — | — |

いずれも基本波が突出しており（第2ピークの強度は 0.12 以下）、周期の取り違えは起きていない。実物の 0.2321 紐幅は、正規化後の帯で約60pxにあたる。Task 005H で信用できなかった測定は、紐が90px程度・特徴が30px程度で分解能の限界に重なっていたが、今回は紐幅が260pxに正規化されており条件が違う。

とはいえ、これは1枚の写真の1つの読み方でしかない。**目視の1.8を否定するものとしては扱わず、両方に耐える値を選んだ。**

### 山形の数え方について（次に読む人へ）

比較画像で「山形」を数えるとき、**レンダー側で色のペアを1つと数え、実物側で形を1つと数えると、2倍ずれる。**

レンダーでは隣り合う糸の走りが別の色になるため、青のV・桃のVが交互に並ぶ。実物の中央は全部橙なので色では分けられない。構造としては、レンダーの1つのV＝実物の1つのVである。色のペア（青＋桃）は、上下の交互（over／under）1組にあたり、これが「山形1つ」である。実物でも上下1組が山形1つなので、色のペアと形の1組を対応させるのが正しい。

本タスクの 1.8／1.3／3.2 という数はこの定義（上下1組＝山形1つ）で一貫している。モデル側では `4 × 紐幅 ÷ 1リピート長` に等しく、縦横比だけで決まる。
