## 目的

展開図の1リピートは全周と同じ長さの正方形であるべきところ、3Dでは軸方向に約3.55倍つぶれている。この巻き付けのアスペクト比を正本から導出する形へ直し、畝の傾きを実物と同じおよそ45度にする。

模様の内容（どの位置の糸がどのパッチを占めるか）は変更しない。変えるのは、その模様をどの寸法の立体へ写すかである。

## 確認された事実

### 展開図の素データ

`MaruGenjiSurfacePatternGenerator.normalizedCorners` の座標系は次のとおり。

- 周方向 `u`: `x ∈ [50, 450]` を `[0, 1]` へ写す。8列 × 50単位 = 400単位が全周にあたる。
- 長手方向 `v`: `(y - faceTop) / 400`。1リピートが400単位。

したがって1リピートの展開図は 400 × 400 の正方形であり、各パッチの山形は軸に対して45度である。実物写真（`bookA-p94-title-and-finished-braid-closeup.png`）の畝も、軸に対しておよそ45度で一致する。

### 現在の巻き付け

`MaruGenjiSurfaceMeshGenerator` の既定値は次のとおり。

| 項目 | 値 |
| --- | --- |
| `defaultRadius` | 0.48 |
| 全周 `2π × 0.48` | 3.016 |
| `defaultLength` | 3.4 |
| `defaultPatternRepeatCount` | 4 |
| 1リピート長 `3.4 / 4` | 0.85 |
| アスペクト `0.85 / 3.016` | **0.282**（1.0であるべき） |
| 軸方向の圧縮 | **3.55倍** |
| 畝の傾き `atan(3.016 / 0.85)` | **74.3度**（実測の約74度と一致） |

`defaultRadius` と `defaultLength` が互いに独立なハードコード値であることが原因である。これは Task 005E が入れた不具合ではなく、Task 004 で表面を円筒へ写した時点から存在する。

### 2D展開図も同じ問題を持つ

`MaruGenjiThumbnailView` は展開図を `size.width * v / repeatCount` × `size.height * u` でカード寸法いっぱいに引き伸ばしている。山形の角度がカードのアスペクト比次第で決まるため、幾何としては未定義であり、2Dと3Dで同じ模様が別の角度で表示されている。

### 「山形のピッチが実物より細かい」は追わないと判断した

実装報告に、実物写真と比べて山形のピッチが細かい（レンダー約0.4／写真約0.6）という所見があった。次の2点から、本件は追わないと判断する。同じ写真を見て再び同じ疑いを持たないよう記録する。

**1. アスペクト比では原理的に直せない。** 8列×8行・アスペクト1のとき、畝の傾き45度とピッチ `πD/8` は同時に決まる従属量であり、独立に動かせない。「角度は合うがピッチだけずれる」状態は定義上あり得ない。仮に本当にピッチだけずれているなら、それは格子の列数、すなわち64パッチの模様データ自体の問題であって、巻き付けのアスペクト比の問題ではない。

**2. 測り直すと解像度アーティファクトだった。** 帯を切り出して2D FFTで畝の垂直方向間隔を測る同一手法で比較した結果は次のとおり。

| 対象 | 畝間隔 ÷ 紐幅 |
| --- | --- |
| 実物写真（`bookB-p22-23-finished-samples.png` の丸源氏a、帯幅46px） | 0.316 |
| レンダー（帯幅229px） | 0.177 |
| レンダーを46px幅へ縮小して再測定 | 0.277 |

同じ解像度に揃えると差は1.14倍まで縮む。当初見えた1.5〜1.8倍差は、高解像度のレンダーと46px幅しかない書籍写真を直接比較したことによる。「実物のリピートが全周よりやや長い可能性」は、この写真からは支持されない。

より高解像度の実物写真または実測寸法が手に入った場合に限り、再検討する。

#### 訂正（2026-09-04、Task 005H 作成時）

**上の判断は誤りだった。** より高解像度の実物写真（`.build/task005h-references/both-braids-flat-topdown.png`、丸源氏と平源氏を平置き・真上から同一縮尺で撮影）が得られ、当時の条件が満たされたため再検討した結果、次が判明した。

- **差の向きが逆だった。** レンダーは実物より細かいのではなく、**粗い**。丸源氏の周には約16本の糸が並んでいるが、モデルは周方向8列で構成されており、描かれる畝が実物の約2倍太く、行間隔も約2.5倍広い。
- **原因はアスペクト比ではなく周方向の列数だった。** 当時「8列×8行・アスペクト1のとき角度とピッチは従属量であり、アスペクト比では原理的に直せない。仮にピッチだけずれているなら格子の列数の問題である」と書いた指摘そのものは正しかった。誤っていたのは、続けて「解像度アーティファクトなので追わない」と結論したほうである。46 px 幅しかない書籍写真を基準に差の有無を判定したのが早計だった。
- **本タスクで設定したアスペクト比1.0（畝45度）は、実物よりやや粗い。** 紐幅あたりの山形の数は、実物が約1.8に対し本タスク後は約1.3で、約1.4倍粗い。方向としての修正は正しく、本タスク以前の74度へ戻すべきではない。

（2026-09-04 追記）上の訂正で「64パッチを16列×4行として読むとアスペクトは0.20付近になる」と書き、Task 005H でそれを実装させたが、**これも誤りだった**。0.20では実物の約1.8倍細かくなる。根拠としたFFT測定が、紐の写り込みが小さすぎて分解能の限界に達していた。詳細は `docs/tasks/005h-braid-thread-scale.md` の差し戻し節を参照。周方向の列数は8列のまま、縦横比だけを0.72付近へ調整する方針を `docs/tasks/005i-maru-genji-chevron-density.md` で扱う。

修正は `docs/tasks/005h-braid-thread-scale.md` で扱う。

#### 訂正内容の確認（2026-09-04、Task 005H 実装後）

上の訂正を実装結果と突き合わせた。3点とも成り立っている。

- 差の向きが逆だったこと、原因が周方向の列数だったことは、そのとおりだった。展開図の下半分（5〜8行目）が上半分と1パッチも違わない複製であることが素データから確認でき、これを長手方向ではなく周方向へ置き直すと、パッチを1枚も作らずに周16列×4行になる。
- アスペクト比は 0.20 ちょうどになった（16列・4行・傾き `tan(51.3°) = 1.25` から導出）。畝の傾きは全64セグメントで軸から51.34度である。
- 行間隔は本タスクの `C/8 = 0.125C` から `0.2C/4 = 0.05C` へ変わり、訂正が予告した2.5倍がそのまま出た。

なお本タスク当時の「8列×8行・アスペクト1のとき、角度とピッチは従属量である」という指摘は、16列×4行でも同じく成り立つ。列数と行数を決めれば角度もピッチも決まり、アスペクト比はその従属量である。

### 引き続き残っている乖離

撚りの縞角度が2つの山形方向で分かれる（20.1度／53.8度。Task 005E 時点は 26.4／34.6）。正方形リピートで2方向が直交した結果、ストランド局所座標のせん断が方向ごとに逆符号になり、共有テクスチャ1枚では両立できない。撚りの向き（ハンド）は全ストランドで一致している。実物は全ストランドで撚り角が同じであるため、これは見た目としての誤りである。`docs/tasks/005g-maru-genji-twist-direction.md` で扱う。

この件により、Task 005E のテスト `twistKeepsOneHandAndOneAnglePerChevronDirection` を現状を明記する内容へ書き換えている。挙動の変更を伴うテスト書き換えのため、レビュー時に確認すること。
