## 目的

丸源氏と平源氏を「同じ太さの糸で組む」という前提の上に置き直し、糸幅を長さの正本として周方向のスケールを確定する。

現在、丸源氏の表面は周方向8列で構成されている。実物写真の実測では周に約16本が並んでおり、モデルは糸幅に対して周長が半分である。結果として、描かれる畝が実物の約2倍太く、行間隔も約2.5倍広い。角度は Task 005F でほぼ正しくなったが、目の細かさが合っていない。

平源氏についても、同じ糸幅から断面を導出できる状態にする。現在の `defaultHalfWidth = 0.72` / `defaultHalfThickness = 0.12`（比6:1）は根拠がなく、実測から導かれる比（約3.4:1）と一致しない。

本タスクは物理シミュレーションではない。模様の内容（どの位置の糸がどのパッチを占めるか）を作り変えることも目的にしない。

## ここから導かれる値

糸幅を `d` とする。

- 傾き51.3度は「列ピッチ ÷ 行ピッチ = tan(51.3°) = 1.25」を意味する。
- 丸源氏の64パッチを **16列 × 4行** として読むと、周長 = `16d`、1リピート = `4 × (d / 1.25)` = `3.2d`。
- したがって **丸源氏のアスペクト比 ≈ 0.20**（Task 005F で設定した 1.0 ではない）。
- このとき糸の傾きは51度付近に保たれる。Task 005F 以前の74度へ戻るのではない。

平源氏は、

- 周長 = `16d`
- 厚み = `2d`（表裏2枚の貼り合わせ）
- 丸端の断面として周長を保つと、幅 ≈ `6.87d`
- したがって **幅 : 厚み ≈ 3.4 : 1**

作者の言う「幅は8本分」は面を横切る糸の本数であり、投影幅としては縁の2本が回り込むぶん約6.9本分になる。両者は同じことを述べている。

### 糸幅をどこで宣言し、寸法をどう導出したか

`Kumihimo/Domain/BraidThreadScale.swift` を新設した。ここが両プリセット共通の物差しである。

- `displayThreadWidth`: 糸幅1本ぶんをシーン単位で表した値。丸源氏の直径を従来どおり 0.96 に保つ表示用の倍率として `maruGenjiPreviewDiameter * π / columnCount` から求める。すべての導出寸法へ等しくかかるため、比は一切動かない。糸幅の意味そのものは表示の都合と切り離してある。
- `roundBraidRadius(columnCount:threadWidth:)`: 周長が糸 `columnCount` 本分になる半径。
- `flatBraidHalfThickness(threadWidth:)`: 糸幅そのもの（表裏2枚で厚み2本分）。
- `flatBraidHalfWidth(columnCount:threadWidth:)`: 周長が糸 `columnCount` 本分になる丸端断面（2つの平らな面＋半円の縁、周長 `2(幅 − 厚み) + π × 厚み`）を幅について解いた値。

ハードコードを外した箇所は次のとおり。

- `MaruGenjiSurfaceMeshGenerator.defaultRadius`: `0.48` → `roundBraidRadius(columnCount: 16)`。
- `HiraGenjiSurfaceMeshGenerator.defaultHalfThickness`: `0.12` → `flatBraidHalfThickness()`。
- `HiraGenjiSurfaceMeshGenerator.defaultHalfWidth`: `0.72` → `flatBraidHalfWidth(columnCount: 16)`。
- `BraidPresetCatalog.hiraGenji` の `.flat(widthToThicknessRatio: 6)` → 同じ導出から算出。
- 断面比のガード `4...8` → `HiraGenjiSurfaceMeshGenerator.widthToThicknessRatioRange = 2.5...5`。

`HiraGenjiSurfacePatternGenerator.columnCount = 16`（表6＋裏6＋縁2×2）を追加し、平源氏の周方向の本数も区画構成から導出される値にした。

### 丸源氏の64パッチは16列×4行として再構成できた

**採った読み方は「半周説」だが、素データを調べた結果、単純な半周ではなく2行ぶんの滑り（グライド）を伴う半周だった。**

素データを展開すると、8列×8行の格子が隙間なく埋まる。ここで2つの事実が見つかった。

1. **下半分は上半分の完全な複製である。** 5〜8行目は1〜4行目と、糸番号・山形の向き・交差の上下がすべて一致する。つまり展開図は1リピートを2回描いている。
2. **2行離れた行どうしは、列ごとに「盤を半回転させたときの相手の糸」である。** 1行目 `16,1,12,13,8,9,4,5` に対し3行目は `9,8,5,4,1,16,13,12` で、north↔south・east↔west の入れ替え（16→9、1→8、12→5、…）と列ごとに完全に一致する。8列×4行の32か所すべてで成り立つ。

2 が、下半分を周方向のどこへ置くかを決めた。下半分を**2行先へずらして**周方向の反対側へ置くと、周16列 × 長手4行の格子が64セルちょうど埋まり、次がすべて成立する。

- 交差の市松（`column + row` の偶奇）が保たれる。列オフセット8も行オフセット2も偶数なので偶奇が動かない。
- 16か所すべての列の継ぎ目でパッチの辺が過不足なく合う（隙間・重なりなし）。
- 反対側の列には、その糸ではなく**その糸の半回転の相手**が来る。糸1本が同じ高さで紐の両側に同時に存在する、という物理的にありえない状態にならない。

ずらし量0（下半分をそのまま反対側へ置く）でも算術的には成立するが、それは採らなかった。ずらし0だと反対側の列に同じ糸番号が来てしまい、上の最後の点を満たさない。また相手の糸と色が違う配色では、実物なら区別できるはずの表裏が強制的に同じ模様になる。

ずらし量は `MaruGenjiSurfacePatternGenerator.halfTurnGlideRows = 2` として宣言し、その根拠をコメントに残した。素データ（`sourceStrands`、`faceTopByColumnX`）は1文字も変更していない。変えたのは `normalizedCorners` の写し先だけである。

### 挙動を変えたテスト（レビュー時に確認すること）

3件ある。いずれも書き換えの理由をテスト内のコメントへ残した。

1. **`MaruGenjiSurfacePatternTests.threeVerifiedFixturesKeepTheirFixedSpatialSignatures`** — Fixture 1 と 3 の署名文字列を更新した。この署名はパッチを「(v, u) 順に読み出した色の並び」であり、格子の形が 8×8 から 16×4 へ変われば並び順が変わる。両立しないことは証明できる。署名を保つには読み出し順を保つ写像しかなく、それは行オフセットが奇数になるため交差の市松が壊れる。つまり「署名を保つ」と「交差の上下を保つ」は同時に満たせない。後者を選んだ。

   色そのものが変わっていないことは、追加した `eachSignatureRowPairsAnOldRowWithTheOneTwoRowsAhead` が保証する。新しい署名の各行が「旧署名の行」＋「その2行先の行」であることを Fixture 3件すべてで確認しており、パッチが1枚でも糸や色を変えていればこれは成り立たない。Fixture 2 の署名は偶然そのまま変わらなかった。

2. **`BraidStrandSurfaceTests.oneThreadAlternatesOverAndUnderAlongItsLength`** — 4本の runs を長手位置だけで並べて交互性を見る形をやめ、近い半周・遠い半周それぞれの2本ずつで見る形にした。糸1本は同じ高さで紐の両側に現れるため、長手位置だけでは順序が定まらない。上下が2枚ずつであること、各半周内で交互になることは引き続き検証している。

3. **`HiraGenjiSurfaceMeshTests.repeatedTileGeometryNormalsBoundaryAndFiberPhaseMatch`** — 座標を100万倍して整数へ丸めた文字列の完全一致から、許容誤差付きの数値比較へ変えた。タイルの両端は別の計算経路（最初のリピートの前縁と最後のリピートの後縁）で求まるため、単精度で 5.4e-7 だけ違う。従来の半幅・半厚は偶然この丸めをまたがなかっただけで、幾何の連続性そのものは変わっていない。

## 差し戻し（2026-09-04）

本タスクは実装後に差し戻した。**実装の欠陥ではなく、本書が与えた前提が誤っていた。**

### 何が誤っていたか

本書は実物写真のFFT測定から「丸源氏の周には約16本」「糸の傾きは軸から51.3度」を導き、64パッチを16列×4行として読み替えるよう指示した。この測定は信用できるものではなかった。

- 紐が写真上で150〜180pxしかなく、糸1本が約30px、撚りの縞が約15pxで、FFTの分解能とエイリアシングの限界に重なっていた。周期がFFTのグリッド値（96/48/32/24/16…）へ吸着しており、値として意味をなさない。
- 「列数2倍」と「行数2.5倍」を同時に効かせたため、模様の密度が約5倍になり、大きく行き過ぎた。
- Task 004 で実物3例と照合して作った展開図の読み方を、この測定を根拠に変えさせた。**照合済みの展開図のほうが強い証拠であり、重みづけが逆だった。**
